Authentication

Authentication proves that a visitor is allowed to act as a particular user. Prefab Auth can authenticate with a password, PIN, login token or social provider. The login name is configurable too: a project may accept email only, usernames only, or several kinds of identifier.

1. Install Auth

Install the authentication package in the same tutorial project used by Users. Auth owns authentication credentials and sessions; the Users module continues to own profile information such as name, email and active status.

composer require tihloh/prefab-auth

2. Load the existing user

Create public/login.php. Begin by loading the same user source from the Users tutorial:

<?php
require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Users\Mapping\UserMap;
use Tihloh\Prefab\Users\Repositories\PdoUserProvider;
use Tihloh\Prefab\Users\Services\UserManager;

$pdo = new PDO(
    'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
    'root',
    '',
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
);

$map = new UserMap(table: 'users');
$users = new UserManager(new PdoUserProvider($pdo, $map));

$alice = $users->findByEmail('alice@example.com');

At this point Alice is only an identity. No password has been checked yet. Auth will use Alice's user ID to attach authentication credentials without changing the users table.

Checkpoint: $alice should contain the Alice record created in the Users tutorial.

3. Create AuthManager

Add the Auth manager:

use Tihloh\Prefab\Auth\Services\AuthManager;

$auth = new AuthManager([
    'database' => $pdo,
]);

AuthManager is the main authentication API. Because Prefab Users is already registered, Auth can discover its user provider. The PDO connection gives Auth somewhere to store password hashes, PIN hashes and login tokens.

Auth uses separate tables such as prefab_auth_credentials, prefab_auth_pins and prefab_auth_login_tokens. These are authentication data, not profile fields.

4. Set Alice's password

A newly created user has no password until one is assigned:

$auth->setPassword($alice->id, 'secret123');
echo 'Password created';

setPassword() receives the real password but stores only a secure password hash. The plain text password is not written to the database.

Open http://127.0.0.1:8000/login.php, verify the message, then remove these temporary lines so the password is not reset on every request.

5. The first argument is an identifier, not an email

Auth does not assume that every project uses email as its login name. The first argument to attempt() is called an identifier.

$result = $auth->attempt(
    'alice@example.com',
    'secret123'
);

The default identifier mode is any. An accepted identifier is passed to the configured user provider, which decides which user it represents.

With the Prefab Users adapter, common identifier fields are:

email
username
user
login

This lets one project accept email while another project accepts usernames without changing the password API.

6. Add a username to the tutorial user

The current tutorial table contains email but not username. Add one so both forms of login can be tested:

ALTER TABLE users
ADD username VARCHAR(100) NULL UNIQUE;

UPDATE users
SET username = 'alice'
WHERE email = 'alice@example.com';

Tell Prefab Users that username is an additional user attribute. Replace the simple map with:

$map = new UserMap(
    table: 'users',
    attributes: [
        'username' => 'username',
    ],
);

Now both of these can identify Alice when Auth uses the default any policy:

$auth->attempt('alice', 'secret123');
$auth->attempt('alice@example.com', 'secret123');
Checkpoint: Both the username and email should authenticate with the same password.

7. Make a project email-only

Some projects intentionally use email as the only valid login name. Set the identifier rule explicitly:

$auth = new AuthManager([
    'database' => $pdo,
    'identifier_mode' => 'email',
]);

Auth validates the identifier before asking the provider to find a user. In this mode, alice is rejected because it is not an email address, while alice@example.com is accepted.

Username-only projects can use:

'identifier_mode' => 'username',
'username_pattern' => '/^[A-Za-z0-9._-]{3,50}$',

The default remains any because a reusable Auth module should not decide the project's account naming rule.

8. Create the login form

Because the input may contain an email or username, name the field identifier and use a normal text input instead of type="email".

Add the POST handler:

$message = '';

if (isset($_POST['login'])) {
    $result = $auth->attempt(
        $_POST['identifier'] ?? '',
        $_POST['password'] ?? '',
    );

    $message = $result->success
        ? 'Login successful.'
        : 'Invalid login.';
}
?>

Then add the form:

<h1>Login</h1>
<p><?= htmlspecialchars($message) ?></p>

<form method="post">
    <p>
        <input name="identifier"
               placeholder="Email or username"
               required>
    </p>
    <p>
        <input name="password"
               type="password"
               placeholder="Password"
               required>
    </p>
    <button name="login" value="1">Login</button>
</form>

The browser posts both values to PHP. Auth resolves the identifier, verifies the password hash, checks that the account is active and stores the user ID in the session.

9. Read the current session

All successful login methods create the same authenticated session. Add this above the form:

<?php if ($auth->check()): ?>
    <p>Logged in as user #<?= htmlspecialchars((string) $auth->id()) ?></p>
<?php endif; ?>

The common session API is:

$auth->check(); // Is a user signed in?
$auth->id();    // Current user ID
$auth->user();  // Reload the current user identity
$auth->logout();

Only the user ID needs to live in the session. user() asks the configured provider for the current user when the application needs the full identity.

10. Add PIN authentication

A PIN is another secret credential. It is useful for controlled devices, kiosks or quick re-authentication, but short PINs are easier to guess than strong passwords and should be rate-limited.

Assign Alice a PIN once:

$auth->setPin($alice->id, '1234');

Like passwords, PINs are hashed before storage. The default policy accepts 4 to 12 digits.

Test a PIN login:

$result = $auth->attemptPin(
    'alice',
    '1234'
);

PIN login still uses the same identifier rules and creates the same normal Auth session.

A project that requires exactly six digits can configure:

'pin_pattern' => '/^\d{6}$/',

11. Add a PIN form without replacing the password form

Password and PIN are separate login methods. A page may provide tabs, buttons or separate screens. A simple second form can be:

<form method="post">
    <input name="identifier" placeholder="Email or username" required>
    <input name="pin" inputmode="numeric" placeholder="PIN" required>
    <button name="pin_login" value="1">Login with PIN</button>
</form>

Add its handler:

if (isset($_POST['pin_login'])) {
    $result = $auth->attemptPin(
        $_POST['identifier'] ?? '',
        $_POST['pin'] ?? '',
    );
}

12. Remember only the login name

A common checkbox means “remember my email/username”. This does not need Auth to remember a password. The UI can store only the identifier in a normal cookie and use it to prefill the next form.

For example, after a successful login:

setcookie(
    'remembered_identifier',
    $_POST['identifier'],
    time() + 30 * 86400,
    '/'
);

Then prefill the input:

value="<?= htmlspecialchars(
    $_COOKIE['remembered_identifier'] ?? ''
) ?>"

This is different from remembering authentication. The next visit still requires a password or another credential.

13. Remember authentication for only the next login

Do not save the user's plain password just to skip one future password prompt. Auth can issue a one-time token instead:

$token = $auth->createNextLoginToken(
    $alice->id
);

The default lifetime is 24 hours. Store the returned token in an HttpOnly cookie:

setcookie('next_login', $token, [
    'expires' => time() + 86400,
    'path' => '/',
    'secure' => true,
    'httponly' => true,
    'samesite' => 'Lax',
]);

On the next visit, before showing the login form:

if (!$auth->check() && isset($_COOKIE['next_login'])) {
    $result = $auth->attemptToken(
        $_COOKIE['next_login'],
        'next_login'
    );

    setcookie('next_login', '', time() - 3600, '/');
}

The token is single-use. Even if the browser cookie is not deleted, the same token cannot authenticate a second time.

14. Keep me logged in

“Keep me logged in” is different from a normal PHP session because browser sessions may expire. Auth can create a longer-lived remember token:

$token = $auth->createRememberToken(
    $alice->id
);

Store it in an HttpOnly Secure cookie. On later requests, use it only when the ordinary session is missing:

if (!$auth->check() && isset($_COOKIE['remember_login'])) {
    $auth->attemptToken(
        $_COOKIE['remember_login'],
        'remember'
    );
}

The default remember-token lifetime is 30 days. It remains usable until it expires or is revoked.

To invalidate remembered logins for a user:

$auth->revokeLoginTokens(
    $alice->id,
    'remember'
);

A real logout screen should normally clear the remember cookie too. “Log out all devices” should revoke persistent tokens.

15. One-time token login

A project may want a magic link, temporary access code, device handoff or another passwordless flow. Create a short-lived one-time login token:

$token = $auth->createLoginToken(
    $alice->id
);

The default lifetime is 15 minutes. Only the token hash is stored server-side.

Authenticate it with:

$result = $auth->attemptToken($token);

After a successful use, the token cannot be used again.

16. Accept a token from the login UI

A token does not have to come from a link. It may be pasted or typed into a form:

<form method="post">
    <input name="token" placeholder="Login token" required>
    <button name="token_login" value="1">Login with token</button>
</form>

Handler:

if (isset($_POST['token_login'])) {
    $result = $auth->attemptToken(
        $_POST['token'] ?? ''
    );
}

17. URL login is disabled by default

Prefab Auth can read login information from a URL query string, but it does nothing unless the project explicitly enables this feature.

$result = $auth->attemptFromQuery($_GET);

With the default configuration, the result is unsuccessful with reason url_login_disabled.

This is intentional. Passwords placed in URLs can leak into browser history, web-server logs, proxies, analytics tools, screenshots and referrer information.

18. Enable URL login only when the project requires it

To explicitly enable both long and short parameter names:

$auth = new AuthManager([
    'database' => $pdo,
    'url_login' => true,
]);

Then these forms are understood:

/login?user=alice&password=secret123
/login?u=alice&p=secret123

The page still has to call:

$result = $auth->attemptFromQuery($_GET);

Password-in-URL login should normally be limited to controlled legacy/integration cases and HTTPS. It should not be the default login design.

19. Prefer a token in the URL

A short-lived one-time token is safer than exposing the user's reusable password. Enable URL token login while keeping URL passwords disabled:

$auth = new AuthManager([
    'database' => $pdo,
    'url_login' => [
        'allow_token' => true,
        'allow_password' => false,
    ],
]);

Create a token and place only that temporary secret in the link:

$token = $auth->createLoginToken($alice->id);
/login?token=ONE_TIME_TOKEN
/login?t=ONE_TIME_TOKEN

Because normal login tokens are single-use and short-lived, a leaked old URL becomes useless after the token is consumed or expires.

20. Customize URL parameter names

Projects integrating an older system may already use different query names. Configure accepted aliases instead of rewriting Auth:

'url_login' => [
    'user_keys' => ['user', 'u', 'account'],
    'password_keys' => ['password', 'pass', 'p'],
    'token_keys' => ['token', 't'],
],

21. Password management

Auth provides password operations separately from login:

$auth->hasPassword($alice->id);
$auth->verifyPassword($alice->id, 'secret123');

$changed = $auth->changePassword(
    $alice->id,
    'secret123',
    'new-secret-456'
);

$auth->removePassword($alice->id);

verifyPassword() checks a password without changing the session. changePassword() requires the current password. setPassword() is appropriate for an administrator or verified password-reset flow that is allowed to replace the credential directly.

22. PIN management

$auth->hasPin($alice->id);
$auth->verifyPin($alice->id, '1234');
$auth->removePin($alice->id);

Removing a PIN does not remove the password, social accounts or user identity. Each authentication method is independent.

23. Inactive accounts

Every Auth login method still checks whether the user identity is active. Disable Alice through Users:

$users->update($alice->id, [
    'active' => false,
]);

Password, PIN and token authentication should now fail even when the credential itself is correct. Restore the account afterward:

$users->update($alice->id, [
    'active' => true,
]);

This allows an application to disable access while preserving the user record and its history.

24. Understand AuthResult

Authentication methods return a result object instead of redirecting automatically:

$result->success;
$result->user;
$result->reason;
$result->log;

This lets the same Auth package work in normal PHP pages, JSON APIs, CLI tools or another framework. Common failure reasons include invalid_credentials, invalid_identifier, invalid_token and url_login_disabled.

25. Add request information for audit logs

Authentication can include request context:

$result = $auth->attempt(
    $_POST['identifier'] ?? '',
    $_POST['password'] ?? '',
    [
        'ip_address' => $_SERVER['REMOTE_ADDR'] ?? null,
        'user_agent' => $_SERVER['HTTP_USER_AGENT'] ?? null,
    ],
);

The same context parameter is available for PIN and token attempts. It does not change credential verification; it enriches authentication logs.

26. Social login

Social authentication proves identity through an external provider such as Google or GitHub. A social user may therefore sign in without having a local password or PIN.

Start a provider login:

$url = $social->authorizationUrl('google');
header('Location: ' . $url);
exit;

The provider redirects the browser back to the application's callback URL. Complete authentication with:

$result = $social->callback(
    'google',
    $_GET
);

The social resolver decides which local user corresponds to the provider identity. Once resolved, social login establishes the same Auth session used by password, PIN and token login.

Linked provider accounts can be inspected or removed:

$social->accountsForUser($alice->id);
$social->unlink($alice->id, 'google');

27. Advanced identifier rules

If a project uses employee numbers, phone numbers or another special format, a custom validator can decide which identifier strings are acceptable:

$auth = new AuthManager([
    'database' => $pdo,
    'identifier_validator' => function (string $value): bool {
        return preg_match('/^EMP-\d{5}$/', $value) === 1;
    },
]);

A matching user provider then resolves that identifier to the correct user. This keeps format policy and user lookup separate.

28. Advanced storage

The built-in PDO stores are convenient defaults. Larger applications can replace them through interfaces:

AuthCredentialStoreInterface
PinCredentialStoreInterface
LoginTokenStoreInterface

This makes it possible to keep the same Auth API while moving credentials into another database or security service.

29. Which login method should a project use?

Password login is the simplest general-purpose starting point. PIN is useful when the environment justifies a shorter secret and strong rate limiting exists. One-time tokens work well for temporary or passwordless access. Remember tokens are for persistent browser login. Social authentication delegates identity verification to an external provider. URL password login exists for special compatibility cases but should remain disabled unless the project deliberately needs it.
