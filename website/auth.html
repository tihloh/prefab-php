Authentication

Authentication answers a different question from the Users module. Users tells the application who a person is; Auth verifies whether that person knows the correct credential and keeps track of the signed-in session. In this tutorial, Alice remains in the users table while her password is stored separately by Auth.

1. Install

The Auth package provides password verification, session handling and authentication-related storage. Installing it does not change the existing users table.

composer require tihloh/prefab-auth

2. Load Alice from Prefab Users

Authentication needs an identity to authenticate. Instead of creating another user record, reuse Alice from the Users tutorial.

Create public/login.php and connect to the same database:

<?php
require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Users\Mapping\UserMap;
use Tihloh\Prefab\Users\Repositories\PdoUserProvider;
use Tihloh\Prefab\Users\Services\UserManager;

$pdo = new PDO(
    'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
    'root',
    '',
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
);

$users = new UserManager(
    new PdoUserProvider($pdo, new UserMap(table: 'users'))
);

$alice = $users->findByEmail('alice@example.com');

findByEmail() is used because login forms normally begin with an email address or another identifier. At this point no password has been checked; the code has only found the matching user identity.

Checkpoint: $alice should contain the Alice user created in the Users tutorial.

3. Create AuthManager

Add the Auth manager:

use Tihloh\Prefab\Auth\Services\AuthManager;

$auth = new AuthManager([
    'database' => $pdo,
]);

AuthManager is the main API for password operations, login, logout and session lookup. Passing the PDO connection gives Auth a place to store its own credential records.

Because Prefab Users is already registered in the same request, Auth can discover the available user provider and use it to resolve identities. This keeps the responsibilities separate:

Users: id, name, email, active
Auth:  password credential, login, session

The first password-storage operation creates prefab_auth_credentials automatically. The password hash is linked to Alice by her user ID, so no password_hash column is needed in users.

4. Set the first password

A newly created identity does not automatically have a password. Assign one with setPassword():

$auth->setPassword($alice->id, 'secret123');
echo 'Password created';

Pass the user ID rather than the email because IDs are stable internal identifiers. Auth hashes the plain password before storing it; the plain text secret123 is not saved directly in the database.

Open http://127.0.0.1:8000/login.php.

Checkpoint: The page should display Password created. The database should also contain prefab_auth_credentials.

5. Test authentication

Now test the actual login process. Remove the temporary setPassword() lines so the password is not reset every time the page loads, then add:

$result = $auth->attempt(
    'alice@example.com',
    'secret123'
);

echo $result->success
    ? 'Login works'
    : 'Login failed';

attempt() performs the complete password-login check. First it asks the user provider for the identity matching alice@example.com. Then it loads Alice's Auth-owned password hash, verifies the supplied password and checks whether the user is active. If all checks pass, Auth stores Alice's ID in the session.

The method returns an authentication result instead of printing or redirecting automatically. This allows the same Auth code to work in a browser page, an API or another application architecture.

Checkpoint: The correct password should display Login works. Change the password in the test and confirm that it displays Login failed.

6. Create a login form

The hard-coded test proves that Auth works, but real users need a screen where they can enter their own credentials. Replace the hard-coded authentication test with a POST handler:

$message = '';

if (isset($_POST['login'])) {
    $result = $auth->attempt(
        $_POST['email'] ?? '',
        $_POST['password'] ?? '',
    );

    $message = $result->success
        ? 'Login successful.'
        : 'Invalid login.';
}
?>

The handler only runs when the submit button named login is present. The values typed into the form become $_POST['email'] and $_POST['password'].

Add the form:

<h1>Login</h1>
<p><?= htmlspecialchars($message) ?></p>

<form method="post">
    <p><input name="email" type="email" placeholder="Email" required></p>
    <p><input name="password" type="password" placeholder="Password" required></p>
    <button name="login" value="1">Login</button>
</form>

The password input hides the characters visually, but security still depends on HTTPS in a real deployment. The browser submits the password to PHP, and Auth compares it with the stored hash.

Checkpoint: Sign in with alice@example.com and secret123.

7. Read the current session

A successful login should remain valid across page requests. Auth stores the authenticated user ID in the session so the application does not need to ask for the password on every page.

Add this above the login form:

<?php if ($auth->check()): ?>
    <p>Logged in as user #<?= htmlspecialchars((string) $auth->id()) ?></p>
<?php endif; ?>

The three common session methods answer different questions:

$auth->check(); // Is anyone logged in?
$auth->id();    // What is the logged-in user's ID?
$auth->user();  // Load the full user identity.

user() loads the current identity through the configured user provider. This means the session only needs to remember the ID rather than copying the whole user record into session storage.

Checkpoint: Refresh the page after logging in. The authenticated session should remain active.

8. Add logout

Logout removes the authenticated user ID from the session. Add this handler before the login handler:

if (isset($_POST['logout'])) {
    $auth->logout();
    $message = 'Logged out.';
}

Add a logout button inside the logged-in section:

<form method="post">
    <button name="logout" value="1">Logout</button>
</form>

After logout(), check() becomes false and id() returns no authenticated user.

Checkpoint: Log in, refresh the page, and then log out.

9. Check whether a password exists

Some users may be created before a password is assigned, or they may use only social authentication. hasPassword() checks whether Auth currently has a password credential for a user.

if ($auth->hasPassword($alice->id)) {
    echo 'Alice has a password';
}

10. Verify a password without logging in

Sometimes an application needs to confirm a password without starting a new login session, such as before changing sensitive account settings.

$ok = $auth->verifyPassword(
    $alice->id,
    'secret123'
);

This returns a boolean and does not change the current session.

11. Change a password

A normal password-change screen should verify the current password before accepting a new one. changePassword() combines those two steps:

$changed = $auth->changePassword(
    $alice->id,
    'secret123',
    'new-secret-456'
);

If the current password is wrong, the method returns false and leaves the existing credential unchanged. If it returns true, the new password has been hashed and stored.

12. Reset or remove a password

An administrator or password-reset process may be allowed to assign a new password without knowing the old one. In that case, call setPassword() directly:

$auth->setPassword(
    $alice->id,
    'reset-password-789'
);

A password can also be removed:

$auth->removePassword($alice->id);

After removal, password login fails until another password is assigned. The user identity itself remains in the Users module.

13. Inactive accounts

Password correctness is not the only requirement for login. Auth also checks the identity's active status so an account can be disabled without deleting it.

$users->update($alice->id, [
    'active' => false,
]);

After Alice becomes inactive, even the correct password should fail. Restore the account afterward:

$users->update($alice->id, [
    'active' => true,
]);

This separation is useful because disabling the identity immediately affects authentication while preserving the user record for reports, ownership references and audit history.

14. Advanced: request context and logs

Authentication attempts can include information about the HTTP request. This does not affect password verification, but it makes authentication logs more useful.

$result = $auth->attempt(
    $_POST['email'] ?? '',
    $_POST['password'] ?? '',
    [
        'ip_address' => $_SERVER['REMOTE_ADDR'] ?? null,
        'user_agent' => $_SERVER['HTTP_USER_AGENT'] ?? null,
    ],
);

The IP address and user agent can later help answer questions such as where a login came from or which browser was used.

15. Advanced: custom credential stores

The built-in PDO credential store is convenient for normal applications, but Auth does not require passwords to live there. A project can implement AuthCredentialStoreInterface to store credentials in another database, service or security system.

This keeps the Auth API the same even when the underlying password storage changes.

16. Advanced: legacy providers

Older or custom Auth integrations may already return a password hash directly from the user provider through authPasswordHash(). That behavior remains supported as a compatibility fallback.

For new applications, keeping password credentials in Auth-owned storage is usually cleaner because the user profile schema does not need to know how authentication is implemented.

17. Advanced: social authentication

Social authentication verifies identity through an external provider such as Google instead of a local password. Because of that, it is separate from the password credential flow shown above.

$url = $social->authorizationUrl('google');
header('Location: ' . $url);

This redirects the browser to the provider. After the user approves sign-in, the provider redirects back to the application's callback URL:

$result = $social->callback('google', $_GET);

The callback verifies the provider response, resolves the corresponding local user and can establish the same Auth session used by password login.
