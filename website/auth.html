Authentication

Users owns identity. Auth owns passwords and sessions. Start by giving Alice a password through Auth, then build the login screen one slice at a time.

Before starting: complete the basic Users tutorial through creating Alice. The users table only needs identity/profile fields such as id, name, email and active.

1. Install

composer require tihloh/prefab-auth

2. Reuse Alice from Prefab Users

Create public/login.php and begin with the same database and Users setup:

<?php
require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Users\Mapping\UserMap;
use Tihloh\Prefab\Users\Repositories\PdoUserProvider;
use Tihloh\Prefab\Users\Services\UserManager;

$pdo = new PDO(
    'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
    'root',
    '',
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
);

$users = new UserManager(
    new PdoUserProvider($pdo, new UserMap(table: 'users'))
);

$alice = $users->findByEmail('alice@example.com');
Checkpoint: $alice is a real user from the Users module. No password column was added to users.

3. Create AuthManager

Add:

use Tihloh\Prefab\Auth\Services\AuthManager;

$auth = new AuthManager([
    'database' => $pdo,
]);

Because Prefab Users is already loaded, Auth can discover it as the identity source. Because PDO is supplied, Auth can create and use its own credential storage.

Auth storage: the first password operation automatically creates prefab_auth_credentials. Your users table stays unchanged.

4. Give Alice her first password

Add this once:

$auth->setPassword($alice->id, 'secret123');
echo 'Password created';

Open http://127.0.0.1:8000/login.php.

Checkpoint: the page says Password created, and the database now contains prefab_auth_credentials.

5. Test one login

Remove the temporary setPassword() line and replace it with:

$result = $auth->attempt(
    'alice@example.com',
    'secret123'
);

echo $result->success
    ? 'Login works'
    : 'Login failed';
Checkpoint: the correct password works. Change it in the test and confirm login fails.

6. Build a small login form

Remove the hard-coded login test. Add:

$message = '';

if (isset($_POST['login'])) {
    $result = $auth->attempt(
        $_POST['email'] ?? '',
        $_POST['password'] ?? '',
    );

    $message = $result->success
        ? 'Login successful.'
        : 'Invalid login.';
}
?>

Then add the form:

<h1>Login</h1>
<p><?= htmlspecialchars($message) ?></p>

<form method="post">
    <p><input name="email" type="email" placeholder="Email" required></p>
    <p><input name="password" type="password" placeholder="Password" required></p>
    <button name="login" value="1">Login</button>
</form>
Checkpoint: try a wrong password, then sign in with alice@example.com / secret123.

7. Show the current session

Add this above the login form:

<?php if ($auth->check()): ?>
    <p>Logged in as user #<?= htmlspecialchars((string) $auth->id()) ?></p>
<?php endif; ?>

The basic session API is:

$auth->check();
$auth->id();
$auth->user();
Checkpoint: refresh and confirm the session remains.

8. Add logout

Add before the login handler:

if (isset($_POST['logout'])) {
    $auth->logout();
    $message = 'Logged out.';
}

Inside the logged-in section:

<form method="post">
    <button name="logout" value="1">Logout</button>
</form>
Checkpoint: log in, refresh, then log out.

9. Build on it — check whether a password exists

if ($auth->hasPassword($alice->id)) {
    echo 'Alice has a password';
}

10. Build on it — verify without logging in

$ok = $auth->verifyPassword(
    $alice->id,
    'secret123'
);

11. Build on it — change password

$changed = $auth->changePassword(
    $alice->id,
    'secret123',
    'new-secret-456'
);

After it returns true, the old password should fail and the new password should work.

12. Build on it — set/reset a password directly

An admin or password-reset flow can replace the password without knowing the old one:

$auth->setPassword(
    $alice->id,
    'reset-password-789'
);

Remove a password completely:

$auth->removePassword($alice->id);

13. Build on it — inactive accounts

Auth still respects identity status from Users:

$users->update($alice->id, [
    'active' => false,
]);

Log out and try signing in. Restore Alice afterward:

$users->update($alice->id, [
    'active' => true,
]);

14. Advanced — request context and logs

$result = $auth->attempt(
    $_POST['email'] ?? '',
    $_POST['password'] ?? '',
    [
        'ip_address' => $_SERVER['REMOTE_ADDR'] ?? null,
        'user_agent' => $_SERVER['HTTP_USER_AGENT'] ?? null,
    ],
);

15. Advanced — custom credential stores

Auth's built-in PDO store is only the default. A project can provide another implementation of AuthCredentialStoreInterface when credentials belong in another service or storage system.

16. Advanced — legacy providers

Existing providers that already expose a password hash through authPasswordHash() continue to work as a fallback. New applications do not need to put passwords on their user model.

17. Advanced — social authentication

Social login stays separate from password storage. Configure provider credentials and callback URLs only when you are ready for OAuth.

$url = $social->authorizationUrl('google');
header('Location: ' . $url);

Callback:

$result = $social->callback('google', $_GET);
Finished: identity remained in Users, passwords remained in Auth, and the tutorial progressed from setting one password to a complete login/session flow without modifying the user table.
