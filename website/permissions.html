Permissions

Authentication answers “who is the user?” Permissions answers “what is that user allowed to do?” This tutorial defines two permissions, stores user and group overrides, and shows how Prefab decides the final result.

1. Install Permissions

composer require tihloh/prefab-permissions

The module separates permission definitions from permission overrides. A definition describes an action and its default state. An override changes that state for a specific user or group.

2. Define the available permissions

Create config/permissions.php:

<?php
return [
    'documents.view' => [
        'name' => 'View Documents',
        'description' => 'Can view documents',
        'category' => 'Documents',
        'default' => true,
    ],
    'documents.approve' => [
        'name' => 'Approve Documents',
        'description' => 'Can approve documents',
        'category' => 'Documents',
        'default' => false,
    ],
];

The array key such as documents.approve is the machine-readable permission ID used by code. The name and description are human-friendly labels for an admin screen. The default is used only when no user or group override applies.

This means a new user can view documents by default, but cannot approve them until a rule grants that permission.

3. Represent the subject being checked

Create public/permissions.php and begin with:

<?php
require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Permissions\Contracts\PermissionSubjectInterface;
use Tihloh\Prefab\Permissions\Repositories\PdoPermissionStore;
use Tihloh\Prefab\Permissions\Services\PermissionManager;

final class TutorialSubject implements PermissionSubjectInterface
{
    public function __construct(public int $id, public array $groups = []) {}
    public function permissionSubjectId(): int|string { return $this->id; }
    public function permissionGroupIds(): array { return $this->groups; }
}

Permissions does not require a specific User class. Instead, it asks for a small contract: the subject's ID and the IDs of groups it belongs to. This keeps the module usable with Prefab Users or another application's user model.

4. Connect storage and definitions

$pdo = new PDO(
    'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
    'root',
    '',
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
);

$permissions = new PermissionManager(
    __DIR__ . '/../config/permissions.php',
    new PdoPermissionStore($pdo),
);

PermissionManager performs resolution. PdoPermissionStore persists overrides. The store automatically creates prefab_subject_permissions, so the application does not have to design a table just to test the module.

5. Create a test user and group

$userId = (int) ($_GET['user'] ?? $_POST['user'] ?? 1);
$groups = [10];
$user = new TutorialSubject($userId, $groups);

This tutorial treats user #1 as a member of group #10. The actual group does not need a separate table for this demonstration because Permissions only needs the group ID during resolution.

6. Allow, deny or clear an override

Add the POST handler:

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $permission = $_POST['permission'] ?? 'documents.approve';
    $scope = $_POST['scope'] ?? 'user';
    $id = $scope === 'group' ? 10 : $userId;
    $action = $_POST['action'] ?? 'clear';

    if ($action === 'allow') $permissions->set($scope, $id, $permission, true);
    if ($action === 'deny')  $permissions->set($scope, $id, $permission, false);
    if ($action === 'clear') $permissions->clear($scope, $id, $permission);
}

$results = $permissions->resolvedFor($user);

set(..., true) creates an explicit allow. set(..., false) creates an explicit deny. clear() removes the override completely, which is different from denying. Once cleared, the decision falls back to another source such as a group or the definition default.

The form lets you change both the permission and the scope. The hidden user field preserves the selected user ID across POST requests.

8. Display the effective result

<h2>Effective permissions</h2>
<pre><?php
foreach ($results as $id => $result) {
    echo $id . ' = ' . ($result->allowed ? 'ALLOW' : 'DENY') . ' via ' . $result->source . PHP_EOL;
}
?></pre>

The important part is $result->source. It explains why the result is allow or deny, not only the final boolean.

9. Understand resolution order

User override
    ↓ if absent
Group overrides
    ↓ if absent
Definition default

A user-specific rule is the most precise, so it wins. If there is no user rule, Prefab considers the user's groups. If no group supplies a decision, the permission definition's default is used.

Test the sequence: clear everything and observe defaults; allow documents.approve for group #10; deny it for user #1; then clear the user deny. The group allow should become effective again.

10. Inspect raw overrides

print_r([
    'user' => $permissions->overridesFor('user', $userId),
    'group10' => $permissions->overridesFor('group', 10),
]);

Raw overrides show only explicitly stored rules. They are useful when building an admin screen that must distinguish “deny” from “inherit.”

11. Direct API

$permissions->set('user', 1, 'documents.approve', true);
$permissions->set('user', 1, 'documents.approve', false);
$permissions->clear('user', 1, 'documents.approve');
$permissions->clearAll('user', 1);

$permissions->can($user, 'documents.approve');
$permissions->resolve($user, 'documents.approve');
$permissions->resolvedFor($user);
$permissions->definitions();
$permissions->definition('documents.approve');
$permissions->defined('documents.approve');

can() is the convenient yes/no check used by application code. resolve() returns the richer result when the caller also needs the decision source. resolvedFor() resolves all definitions for one subject.

12. Diagnostics

print_r($permissions->explain());

explain() helps diagnose which storage and integrations the module resolved at runtime.
