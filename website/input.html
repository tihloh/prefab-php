Input and validation

Input validation is the boundary between raw request data and data the application is willing to trust. This tutorial builds a real form so you can see how Prefab transforms values, rejects invalid input and returns only approved fields.

1. Install Input

composer require tihloh/prefab-input

Prefab Input is standalone. It can validate arrays, form submissions and uploaded files without requiring Database, Users, Routes or Auth.

2. Create a form page

Create public/input.php. Start with the processing code:

<?php
require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Input\Input;

$errors = [];
$valid = null;

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $result = Input::from($_POST)->process([
        'name' => 'trim|required|string|max:100',
        'email' => 'trim|lowercase|required|email',
        'age' => 'required|integer|min:18',
    ]);

    if ($result->fails()) {
        $errors = $result->errors();
    } else {
        $valid = $result->validated();
    }
}
?>

$_POST contains raw values sent by an HTML form. They are strings supplied by the browser, so the application should not assume that an email is valid or that an age is really an integer.

Input::from($_POST) creates an input object from that raw data. process() then applies a rule string to each declared field.

3. Understand the rules

'name'  => 'trim|required|string|max:100'
'email' => 'trim|lowercase|required|email'
'age'   => 'required|integer|min:18'

Rules are processed from left to right. trim removes surrounding whitespace. required rejects a missing or empty value. string checks the expected type. max:100 limits the name length. lowercase transforms email text before it is returned. email checks email syntax. integer validates and converts the age to an integer, and min:18 requires an adult age.

This combination demonstrates an important difference: some rules validate values while others transform them.

4. Add the HTML form

<!doctype html>
<html>
<body>
    <h1>Prefab Input Test</h1>

    <form method="post">
        <p>
            <label>Name<br>
                <input name="name" value="<?= htmlspecialchars($_POST['name'] ?? '') ?>">
            </label>
        </p>
        <p>
            <label>Email<br>
                <input name="email" value="<?= htmlspecialchars($_POST['email'] ?? '') ?>">
            </label>
        </p>
        <p>
            <label>Age<br>
                <input name="age" value="<?= htmlspecialchars($_POST['age'] ?? '') ?>">
            </label>
        </p>
        <button type="submit">Validate</button>
    </form>
</body>
</html>

The HTML name attributes are important because they become the keys in $_POST. For example, name="email" becomes $_POST['email'].

htmlspecialchars() escapes HTML characters before previously submitted text is placed back into the page. This prevents user input such as <script> from being interpreted as page markup.

5. Display validation errors

Add this below the form:

<?php if ($errors): ?>
    <h2>Validation errors</h2>
    <pre><?= htmlspecialchars(print_r($errors, true)) ?></pre>
<?php endif; ?>

fails() means at least one declared field did not pass processing. errors() returns the field-specific error information so a real application can show messages beside the corresponding controls.

6. Display validated data

Add this after the error block:

<?php if ($valid !== null): ?>
    <h2>Validated data</h2>
    <pre><?= htmlspecialchars(print_r($valid, true)) ?></pre>
<?php endif; ?>

validated() is the important output boundary. It returns only fields that were declared in the schema and successfully processed. Extra submitted fields are not automatically trusted just because they arrived in the request.

7. Run the page

php -S 127.0.0.1:8000 -t public

Open http://127.0.0.1:8000/input.php.

8. Test invalid input

Name:   Demo User
Email:  not-an-email
Age:    15

The email fails because it is not valid email syntax. The age becomes an integer but still fails min:18. Seeing both errors confirms that the request reached Prefab and the rules were actually evaluated.

9. Test valid input and transformations

Name:   Demo User
Email:  DEMO@EXAMPLE.COM
Age:    25

The validated result should contain demo@example.com because lowercase transformed the email. The age should be an integer rather than the raw form string "25".

Checkpoint: Invalid input should produce errors. Valid input should produce only name, email and age in cleaned form.

10. Why validate before database code?

Validation answers “is this request acceptable?” Database code answers “how should accepted data be stored?” Keeping those responsibilities separate makes application logic easier to understand and prevents invalid request data from reaching lower layers.

A common flow is:

Browser form
    ↓
Raw request data
    ↓
Prefab Input
    ↓
Validated data
    ↓
Users / Database / service logic

11. Advanced: request and upload helpers

For forms that include files, Input::fromRequest() can collect normal request values and uploaded-file data together. File rules can then validate type, MIME and size before a Files module stores the upload.

Works with other Prefab modules

Prefab Input is intentionally request-focused. It does not auto-save anything, but its validated values and UploadedFile objects are designed to pass cleanly into other modules.

ModuleIntegrationHowWhat happens
FilesDirect compatible handoffUploadedFile → FileManager::storeUploaded()Validate an upload with Input, then pass the validated UploadedFile directly to Files for permanent storage.
UsersDirect compatible handoffvalidated() → UserManager::create/update()Only validated/whitelisted form fields need to be passed to Users. Raw request fields stay out of persistence.
AuthDirect compatible handoffvalidated identifier/password/PINA login form can validate/normalize its fields first, then pass them to attempt() or attemptPin().
Any moduleDirect compatible handoffInputResult::validated()Validated input is plain PHP data, so it can safely become service-method arguments throughout the application.
Important: Input does not automatically call another module because validation should never silently cause a database write, login or file save.
