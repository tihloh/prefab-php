Tutorial · Background

Run secondary work now, outside the web request.

Prefab Background immediately hands instructions to a fixed worker pool through a bounded durable journal. It avoids unlimited process creation, never drops work because workers are busy, and captures the originating event time before any backpressure wait.

This is not a scheduler. Every instruction is due immediately. The journal exists for durability and controlled backpressure, not for application-managed delayed jobs.

1. Install

composer require tihloh/prefab-background

2. Configure the shared journal and worker ceiling

use Tihloh\Prefab\Background\BackgroundManager;

$background = new BackgroundManager([
    'path' => __DIR__ . '/../storage/prefab/background',
    'max_workers' => 2,
]);

The web process and every worker must use the same persistent journal path. In Docker, mount the same storage volume into both services.

3. Register a named handler

$background->handler('report.audit', function (array $payload, $context): void {
    // Perform independent work here.
});

Only registered handler names can be dispatched. Payloads are JSON-safe scalar/array data; Prefab does not serialize arbitrary executable PHP objects into the journal.

4. Hand work off immediately

$receipt = $background->run('report.audit', [
    'report_id' => 125,
    'actor_id' => 7,
]);

The caller waits only for a safe handoff. It does not wait for the handler to finish.

5. Understand timing

occurred_at
= when run() was called in the main process

accepted_at
= when Background safely committed the instruction

processed_at
= when a worker completed it

occurred_at is captured before waiting for capacity, so a saturated worker pool cannot change the event's real application time. requestId + sequence also preserve request-local ordering.

6. Start workers

vendor/bin/prefab-background work

Run the configured number under systemd, Supervisor or Docker. max_workers is enforced with process locks, so starting extra worker commands cannot increase Background concurrency beyond the configured ceiling.

7. Backpressure instead of overload

$background = new BackgroundManager([
    'max_workers' => 2,
    'max_pending' => 1000,
    'max_bytes' => 32 * 1024 * 1024,
]);
capacity available
      ↓
durable handoff
      ↓
return immediately

journal full
      ↓
caller sleeps/waits
      ↓
worker frees capacity
      ↓
handoff
      ↓
return

Background does not drop the instruction, silently execute it synchronously, or create more workers. With finite workers and finite storage, backpressure is the safe consequence of sustained overload.

8. Retries are retained

If a handler throws, its instruction stays in the journal and is retried using bounded exponential backoff. There is no default maximum retry count.

9. Use Background with Logs

$logs = new LogManager([
    'database' => $pdo,
    'background' => true,
]);

$logs->record([
    'action' => 'document.approved',
    'subject_type' => 'document',
    'subject_id' => 1001,
]);

Logs captures occurred_at before handoff. created_at remains the later database persistence time. Installing Background alone does not change Logs; background logging must be explicitly enabled.

10. Inspect health

vendor/bin/prefab-background status

or:

print_r($background->status());

Status reports busy/max workers, pending journal count/bytes and registered handlers.

Checkpoint: The main request can commit an instruction quickly while a fixed worker executes it independently, and the event timestamp remains the time it happened in the caller.
