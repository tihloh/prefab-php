Database

The Database module gives the application one consistent way to work with SQL databases. You will first connect to MariaDB/MySQL, then perform CRUD operations, use raw SQL, wrap work in a transaction and finally explore multiple connections and diagnostics.

1. Install Database

composer require tihloh/prefab-database

The main class used in this tutorial is DatabaseManager. It stores one or more database connections and provides the query builder, raw SQL helpers and transaction API.

2. Create the tutorial database and table

Create a MariaDB/MySQL database named prefab_tutorial. Then create a simple users table:

CREATE TABLE users (
    id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(190) NOT NULL UNIQUE,
    active TINYINT(1) NOT NULL DEFAULT 1,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

The table gives the tutorial real data to work with. id uniquely identifies each row. AUTO_INCREMENT lets the database assign IDs automatically. UNIQUE prevents duplicate email addresses. active is stored as a small integer because MySQL commonly represents booleans as 0 and 1.

3. Configure the first connection

Create database-test.php in the project root:

<?php
require __DIR__ . '/vendor/autoload.php';

use Tihloh\Prefab\Database\Services\DatabaseManager;

$database = new DatabaseManager([
    'connections' => [
        'main' => [
            'driver' => 'mysql',
            'host' => '127.0.0.1',
            'database' => 'prefab_tutorial',
            'username' => 'root',
            'password' => '',
        ],
    ],
]);

var_dump($database->ping('main'));

The name main is an application-defined connection name. It lets the project refer to this database later without repeating its connection settings.

ping('main') checks whether the connection can actually be opened. This is the first test because CRUD examples are meaningless until the database connection itself works.

php database-test.php
Checkpoint: The command should print bool(true).

4. Insert a row

$id = $database->table('users')->insertGetId([
    'name' => 'Demo User',
    'email' => 'demo@example.com',
    'active' => true,
]);
echo "Inserted ID: {$id}";

table('users') starts a query against the users table. insertGetId() inserts the row and returns the automatically generated primary key. Keeping that ID lets the next examples work with the exact row that was just created.

5. Read data

$user = $database->table('users')->where('id', $id)->first();
print_r($user);

where() adds a filter. first() returns the first matching row instead of a list. This is appropriate when searching by a unique ID.

To return several rows:

$active = $database->table('users')
    ->where('active', true)
    ->orderBy('name')
    ->limit(20)
    ->get();
print_r($active);

get() returns a collection of rows. orderBy() controls sorting and limit() prevents an accidentally large result set.

6. Update a row

$database->table('users')->where('id', $id)->update([
    'name' => 'Updated Demo User',
]);

The where() clause is important. Without a filter, an update could affect every row in the table. Prefab's query builder keeps the SQL readable, but the same database safety rules still apply.

7. Delete a row

$database->table('users')->where('id', $id)->delete();

Delete operations are permanent unless the application implements its own soft-delete strategy. Always confirm that the filter targets the intended row before deleting.

8. Use raw SQL when it is clearer

The query builder is convenient, but some SQL is easier to write directly. Prefab does not force every query through the builder.

$rows = $database->select(
    'SELECT * FROM users WHERE active = ?',
    [1],
);
print_r($rows);

$database->statement(
    'UPDATE users SET active = ? WHERE email = ?',
    [false, 'demo@example.com'],
);

The question marks are placeholders. Values are supplied separately so the database driver can bind them safely instead of concatenating untrusted text directly into SQL.

9. Group related changes with a transaction

$database->transaction(function ($db) {
    $db->table('users')->insert([
        'name' => 'Transactional User',
        'email' => 'transaction@example.com',
    ]);
});

A transaction treats several database operations as one unit. If the callback finishes successfully, the transaction is committed. If an exception causes it to fail, the transaction can be rolled back. This matters when partial changes would leave the application in an inconsistent state.

10. Reuse an existing PDO connection

$pdo = new PDO(
    'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
    'root',
    '',
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
);

$database = new DatabaseManager([
    'connections' => ['main' => $pdo],
]);

This is useful in an existing application that already creates PDO itself. Prefab can wrap that connection instead of forcing the project to rebuild its database setup.

11. Advanced: multiple connections

$database = new DatabaseManager([
    'default' => 'main',
    'connections' => [
        'main' => $pdo,
        'logs' => [
            'driver' => 'sqlite',
            'database' => __DIR__ . '/storage/logs.sqlite',
        ],
    ],
]);

$main = $database->connection('main');
$logs = $database->connection('logs');

The default connection is used when no connection name is supplied. Named connections are useful when application data, logs or reporting data live in different databases.

$rows = $database
    ->table('prefab_logs', 'logs')
    ->orderBy('id', 'desc')
    ->limit(20)
    ->get();

Passing 'logs' tells the query builder which configured connection should execute the query.

12. Advanced: access raw PDO

$pdo = $database->connection('main');
$defaultPdo = $database->pdo();

This escape hatch is useful when a PDO-specific API is needed that the higher-level Database API does not expose.

13. Advanced: inspect and change connections at runtime

echo $database->defaultName();
print_r($database->names());
var_dump($database->has('main'));
echo $database->driver('main');
var_dump($database->ping('main'));

$database->set('archive', $archivePdo);
$database->useDefault('archive');

These methods are useful in infrastructure code, tests and applications that choose a connection dynamically.

14. How Database cooperates with other Prefab modules

Other modules do not need to depend directly on the full Database package. They can consume a small shared database capability through DatabaseInterface. This keeps modules independently installable while still allowing them to cooperate when Database is present.

15. Configuration precedence

Direct module instance
    ↓
Module-specific PrefabConfig
    ↓
Common PrefabConfig
    ↓
Auto-discovered database capability
    ↓
Default / clear error

This order answers the question “which configuration wins?” More explicit configuration is preferred over automatically discovered configuration.

16. Diagnostics

print_r($database->explain());

explain() shows how the module resolved its configuration. In a larger Prefab application, PrefabRuntime::inspect() can also show registered modules and shared capabilities.

Works with other Prefab modules

Prefab Database is a shared infrastructure module. Once configured, it publishes a database capability that other compatible Prefab modules can discover and reuse automatically.

ModuleIntegrationHowWhat happens
UsersAutomaticdatabase capabilityUsers can build its PDO-backed provider from the shared database without creating another PDO connection in the Users configuration.
AuthAutomatic when neededdatabase / PDO capabilityAuth can use the available database for its own credentials, PINs and login-token tables while leaving the application users table untouched.
PermissionsAutomaticdatabase capabilityPermissions can create/use its permission store from the shared database.
LogsAutomaticdatabase capabilityLogs can create/use its audit-log repository from the shared database.
Named connectionsAutomatic capabilitydatabase.connection.NAMEModules that support a connection name can target a published named connection instead of the default one.
Important: This is why a larger Prefab application normally configures Database once. Individual modules can still receive an explicit PDO/store when isolation is preferred.
