What actually happens when compatible modules exist

Prefab managers register themselves with PrefabRuntime. During configuration passes, each manager publishes capabilities it can provide and asks the runtime for compatible capabilities it is missing. If a usable resource is discovered, the consuming module configures itself from it. You do not need to manually inject the same resource again.

new DatabaseManager(...);
new UserManager();
new AuthManager();
new LogManager();

// Compatible modules register themselves.
// Prefab re-runs configuration as modules appear.
// Missing resources are discovered and connected.
Important: Auto-discovery fills missing infrastructure only. If you explicitly provide a provider, repository, database, session, map or other supported configuration, your explicit choice wins.

Example: Auth discovers Users automatically

Auth needs a user provider. Users publishes a user_provider capability when it has a usable provider. If Auth was not given its own provider, it checks the runtime for that capability. When the provider came from Prefab Users, Auth automatically wraps Users with its compatibility adapter.

use Tihloh\Prefab\Users\Services\UserManager;
use Tihloh\Prefab\Auth\Services\AuthManager;

$users = new UserManager([
    'database' => $pdo,
    'map' => $map,
]);

// No $userProvider is manually passed here.
$auth = new AuthManager();

$result = $auth->attempt($email, $password);
Users
  │
  ├─ resolves its provider
  └─ publishes: user_provider
                 │
                 ▼
               Auth
                 │
                 ├─ no explicit provider?
                 ├─ discovers user_provider
                 ├─ recognizes prefab-users
                 └─ auto-configures PrefabUsersAuthProvider

Auth also creates its normal NativeSessionStore automatically when no custom session store was supplied. So a compatible Users module plus Auth can require much less wiring than constructing every dependency manually.

Example: Database can configure Users automatically

Users can work with a custom provider or plain PDO, but when Prefab Database is already registered, Users can discover the shared database capability. If no custom user provider was supplied, Users can build its PDO-backed provider from the discovered database and its configured/default mapping.

$database = new DatabaseManager([
    'connections' => [
        'main' => [
            'driver' => 'mysql',
            'host' => '127.0.0.1',
            'database' => 'app',
            'username' => 'app',
            'password' => 'secret',
        ],
    ],
]);

// No PDO object has to be manually passed to Users.
$users = new UserManager([
    'map' => $map,
]);
DatabaseManager
      │
      └─ publishes database capability
                    │
                    ▼
                 Users
                    │
                    ├─ discovers database
                    ├─ applies configured/default UserMap
                    └─ creates PdoUserProvider

Example: Logs becomes a logger for other modules

When Logs has a repository or can build one from an available database, it publishes the logger capability. Auth and Users look for that capability during configuration. If it appears later, Prefab's configuration pass runs again and the modules can pick it up.

$database = new DatabaseManager(...);
$users    = new UserManager(...);
$auth     = new AuthManager();
$logs     = new LogManager();
Logs
 └─ publishes logger
        │
        ├────────────→ Auth
        │              └─ auto logger
        │
        └────────────→ Users
                       └─ auto logger

Auth also publishes something useful

After configuring itself, Auth publishes an actor_provider capability. Other compatible modules can use it to identify the current authenticated actor without importing or requiring Auth directly.

Auth
 └─ publishes actor_provider
            │
            ├────────→ Users / Logs
            └────────→ Permissions-compatible integrations

Declaration order is intentionally flexible

When a manager registers, Prefab re-runs the small configuration pass. That means a capability that was unavailable earlier can be discovered when its provider appears later.

// This can still converge as modules register:
$auth  = new AuthManager();
$users = new UserManager(['database' => $pdo, 'map' => $map]);
$logs  = new LogManager(['database' => $pdo]);

For stricter application bootstraps, you can explicitly mark startup complete:

PrefabRuntime::ready();

Normal applications usually do not need to call ready().

How Prefab chooses a resource

1. Direct module configuration       ← strongest
2. Module-specific PrefabConfig
3. Common PrefabConfig
4. Compatible discovered capability
5. Sensible module default
6. Clear error if unresolved

This is why Auto-Wiring should feel convenient rather than magical: Prefab discovers and configures what is missing, but it never overrides an explicit application decision.

See what was discovered

print_r($auth->explain());
print_r($users->explain());

print_r(PrefabRuntime::inspect());

For Auth, explain() can show whether its user provider came from direct configuration, Prefab configuration or the discovered user_provider capability, and whether a logger was discovered automatically.

The mental model: install/configure a block → it publishes what it can provide → other compatible blocks discover what they need → missing infrastructure is configured automatically → explicit application configuration still wins.
