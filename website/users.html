Users

Build a simple user-management page with plain HTML, then look behind the curtain with Prefab's request call tree.

1. Install

composer require tihloh/prefab-users

2. Connect Users

<?php
require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Users\Services\UserManager;

$pdo = new PDO(
    'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
    'root',
    '',
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
);

$users = new UserManager(['database' => $pdo]);

3. Add a user

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $users->create([
        'name' => trim($_POST['name'] ?? ''),
        'email' => trim($_POST['email'] ?? ''),
        'active' => true,
    ]);
}

$list = $users->all();
<form method="post">
    <input name="name" placeholder="Name" required>
    <input name="email" type="email" placeholder="Email" required>
    <button>Add user</button>
</form>

4. Display users

<h1>Users</h1>
<table border="1" cellpadding="8">
    <tr><th>ID</th><th>Name</th><th>Email</th><th>Status</th></tr>
    <?php foreach ($list as $user): ?>
    <tr>
        <td><?= $user->id ?></td>
        <td><?= htmlspecialchars($user->name ?? '') ?></td>
        <td><?= htmlspecialchars($user->email ?? '') ?></td>
        <td><?= $user->active ? 'Active' : 'Inactive' ?></td>
    </tr>
    <?php endforeach; ?>
</table>
Checkpoint: Submit the form and confirm the new user appears in the table.

5. Find, update and delete

$user = $users->find(1);
$byEmail = $users->findByEmail('alice@example.com');

$users->update(1, ['name' => 'Alice Smith']);
// $users->delete(1);

6. Map an existing table

use Tihloh\Prefab\Users\Mapping\UserMap;

$map = new UserMap(
    table: 'employees',
    id: 'employee_id',
    name: 'full_name',
    email: 'email_address',
    active: 'is_active',
);

$users = new UserManager([
    'database' => $pdo,
    'map' => $map,
]);

7. Developer diagnostic: see what happened behind the curtain

prefab_trace() prints a high-level call tree of Prefab work completed during the current PHP request. Think of it as a Prefab-aware call stack: it groups nested module work under the operation that caused it instead of exposing vendor paths or raw PHP internals.

Put it near the bottom of the page, after the operations you want to inspect:

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $users->create($data);
}

$list = $users->all();
$recent = $logs->recent(20);

prefab_trace();

After adding a user, output can look like this:

├─ Fields: name, email, active

│  └─ Result: yes

│  └─ Table: users

The exact branches depend on the modules installed and the work actually performed. Database operations are nested beneath Users when Users caused them. Sensitive values, raw SQL, vendor paths, class namespaces, passwords and tokens are intentionally kept out of the normal trace.

Detailed mode

prefab_trace(true);

Detailed mode keeps the same call tree but adds timed internal diagnostic steps such as capability and resource resolution. Use it when the normal tree identifies the area but you need to see more of the sequence.

Development only: The trace is printed into the response. Remove or disable it on normal production pages.

8. Focus on Users only

If a request contains many modules and you only want the execution story involving Users, call:

$users->explain();

This is not a configuration-array dump. It prints the traced execution trees involving Users and its nested work. The method itself returns no diagnostic array.

Prefab Users Execution

Users::create [OK]  5.842 ms
├─ Fields: name, email, active
├─ Database::insert [OK]  1.604 ms
│  └─ Table: users
└─ Result: OperationResult

Structured configuration data

Configuration-resolution data is still available when tooling or tests genuinely need it, but it is deliberately separate from the human debugging view:

$data = $users->explainData();

9. Trace vs explain

DiagnosticWhat it showsUse it for
prefab_trace()High-level call trees for the whole current request.Follow application flow across Prefab modules.
prefab_trace(true)The same tree plus timed internal diagnostic steps.Deeper debugging without raw vendor internals.
$users->explain()Only execution trees involving Users.Focus a busy request on one module.
$users->explainData()Structured resolution metadata.Tests, tooling and advanced configuration inspection.

Users owns identity/profile data. Auth owns credentials, Permissions owns authorization, and Logs owns persistent activity history.
