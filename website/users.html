Users

Prefab Users gives an application one consistent way to read and manage users even when the actual database table is different from project to project. This tutorial starts with one record, then gradually builds a small user-management page.

1. Install

The Users package contains the user manager, database provider and mapping classes used in this tutorial. Composer installs the package and makes its classes available through the project autoloader.

composer require tihloh/prefab-users

2. Create the users table

A user needs a place to store identity and profile data. For this first example, the table contains only four fields: an ID, a display name, an email address and an active flag.

CREATE TABLE users (
    id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(190) NOT NULL UNIQUE,
    active TINYINT(1) NOT NULL DEFAULT 1
);

id uniquely identifies each user. email is unique because it is commonly used to find a user during login or account lookup. active lets the application disable an account without deleting the user record.

Add one sample user so there is something to retrieve in the next step:

INSERT INTO users (name, email)
VALUES ('Alice', 'alice@example.com');
Checkpoint: The users table should now contain Alice.

3. Load a user with Prefab Users

Create public/users.php. This first version only connects the package to the table and retrieves one user.

<?php
require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Users\Mapping\UserMap;
use Tihloh\Prefab\Users\Repositories\PdoUserProvider;
use Tihloh\Prefab\Users\Services\UserManager;

$pdo = new PDO(
    'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
    'root',
    '',
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
);

$map = new UserMap(table: 'users');
$users = new UserManager(new PdoUserProvider($pdo, $map));

$user = $users->find(1);
?>
<h1>User</h1>
<p><?= htmlspecialchars($user?->name ?? 'Not found') ?></p>

The three Prefab objects have different jobs. UserMap tells Prefab which table and columns represent a user. PdoUserProvider performs the database queries. UserManager is the API the rest of the application uses, so pages do not need to know how the data is stored.

$users->find(1) asks the manager for user ID 1. The provider queries the mapped table and converts the returned row into a Prefab user object.

Start the PHP development server:

php -S 127.0.0.1:8000 -t public

Open http://127.0.0.1:8000/users.php.

Checkpoint: The page should display Alice. This confirms that the database connection, table mapping and user provider are working together.

4. List all users

find() returns one user. Most user-management screens need every user, so replace it with all():

$list = $users->all();

$list now contains a collection of user objects. Display each one with a loop:

<h1>Users</h1>
<?php foreach ($list as $user): ?>
    <p>#<?= $user->id ?> <?= htmlspecialchars($user->name ?? '') ?> — <?= htmlspecialchars($user->email ?? '') ?></p>
<?php endforeach; ?>

htmlspecialchars() is used before printing user-controlled text so characters such as < and > are displayed as text instead of being interpreted as HTML.

Checkpoint: Alice should appear in the list.

5. Create users from a form

The page can now read users, but it cannot create one. A browser form sends values through POST; the PHP handler passes those values to $users->create().

Add this before $list = $users->all();:

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $users->create([
        'name' => trim($_POST['name'] ?? ''),
        'email' => trim($_POST['email'] ?? ''),
        'active' => true,
    ]);
}

trim() removes accidental spaces from the beginning or end of the submitted values. The user is marked active immediately because this simple form does not yet include an active/inactive option.

Add the form above the user list:

<h2>Create user</h2>
<form method="post">
    <input name="name" placeholder="Name" required>
    <input name="email" type="email" placeholder="Email" required>
    <button>Create</button>
</form>

The name attributes are important because they become the keys in $_POST. For example, name="email" becomes $_POST['email'].

Enter Bob as a second user and submit the form.

Checkpoint: Bob should appear below Alice. That confirms the form, POST handler and Prefab create operation are connected correctly.

6. Find a user

Different pages need different lookup methods. A profile page may know the numeric ID, while a login or account-recovery page often starts with an email address.

$user = $users->find(1);
$byEmail = $users->findByEmail('alice@example.com');
print_r($byEmail?->toArray());

toArray() is useful while learning or debugging because it shows the fields currently available on the mapped user object.

7. Update a user

Updating needs two pieces of information: which user to change and which fields should receive new values.

Add an update handler before loading the list:

if (isset($_POST['rename'])) {
    $users->update((int) $_POST['id'], [
        'name' => trim($_POST['name']),
    ]);
}

The hidden id field identifies the record. Only name is included in the update array, so the email and other fields remain unchanged.

Inside the existing foreach, add:

<form method="post">
    <input type="hidden" name="id" value="<?= $user->id ?>">
    <input name="name" value="<?= htmlspecialchars($user->name ?? '') ?>">
    <button name="rename" value="1">Rename</button>
</form>

The button has name="rename", so the server can distinguish this action from the create form.

Checkpoint: Rename Bob and refresh the page. The new name should remain because it was saved in the database.

8. Active and inactive users

Disabling a user is often safer than deleting the record. Other tables may still refer to that user, and audit history may need the account to remain identifiable.

$users->update($userId, ['active' => false]);

Read the updated value:

$user = $users->find($userId);
var_dump($user?->active);

Later, the Authentication module can use this value to reject login attempts from inactive accounts.

9. Delete a user

Deletion is intentionally disabled by default because it permanently removes data. Enable it only in applications where deleting users is an allowed operation.

$map = new UserMap(
    table: 'users',
    allowDelete: true,
);

After the map allows deletion, remove a user by ID:

$users->delete($userId);
Checkpoint: Create a temporary user, delete it, and confirm that it no longer appears in the list.

10. Custom project fields

Real applications usually store more than name and email. Prefab calls project-specific fields attributes. They are mapped without changing the core Users API.

Add an office field:

ALTER TABLE users
ADD office VARCHAR(100) NULL;

Tell Prefab how the attribute maps to the database column:

$map = new UserMap(
    table: 'users',
    attributes: [
        'office' => 'office',
    ],
    allowDelete: true,
);

The key on the left is the name used by the application. The value on the right is the actual database column. They can be different when working with an existing schema.

The attribute is now available from the user object:

echo $user->office;
echo $user->get('office');
print_r($user->attributes());

Password credentials are intentionally not part of this profile mapping. Authentication owns password storage so the Users module remains focused on identity and profile information.

11. Advanced: map an existing schema

Prefab Users does not require a table to use names such as id, name or email. The map translates Prefab's standard concepts to the column names already used by an application.

$map = new UserMap(
    table: 'employees',
    id: 'employee_id',
    name: 'full_name',
    email: 'email_address',
    active: 'is_active',
    attributes: [
        'office' => 'office_name',
        'position' => 'position_title',
        'employee_no' => 'employee_no',
    ],
);

This is useful when adding Prefab to an existing project because the database does not need to be redesigned just to satisfy the package.

12. Advanced: restrict writes

Some systems should be readable but not editable by this application. For example, an employee directory may be maintained by another HR system.

$map = new UserMap(
    table: 'employees',
    id: 'employee_id',
    name: 'full_name',
    email: 'email_address',
    active: 'is_active',
    allowCreate: false,
    allowUpdate: false,
    allowDelete: false,
);

The application can still retrieve users, but write operations are blocked by the mapping policy.

13. Advanced: diagnostics

When a module behaves differently from what is expected, explain() shows how Prefab resolved its configuration and integrations.

print_r($users->explain());

This is especially helpful once several Prefab modules are installed and some dependencies are discovered automatically.

Works with other Prefab modules

Prefab Users provides identity/profile data and publishes its user provider so other modules can reuse the same users instead of creating another account system.

ModuleIntegrationHowWhat happens
DatabaseAutomaticdatabase capabilityUsers can discover the shared database and create its default PDO user provider automatically.
AuthAutomaticuser_provider capabilityAuth detects Prefab Users and wraps it with the Auth adapter. The same user ID/profile is used for authentication without requiring password fields in the users table.
LogsAutomaticlogger capabilityWhen Prefab Logs is available, create(), update() and delete() activity can be recorded automatically from the structured log payload produced by Users.
Auth → Users logsAutomatic actor contextactor_provider capabilityWhen Auth is present, Users can use the authenticated user ID as the actor for automatic user-management audit records.
PermissionsCompatibleuser ID / groupsThe user ID can be passed directly to PermissionManager. Group membership can be supplied by the Permissions group service or a custom subject adapter.
Important: Users owns profile/identity data. Auth owns credentials. Permissions owns authorization. Logs owns history. Keeping these concerns separate lets them cooperate without duplicating the user record.
