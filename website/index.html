BEFORE WE BUILD

Why Prefab?

Take one common feature: authenticate a user and keep an audit trail. That already crosses three concerns—Users, Auth and Logs.

Without Prefab

// USERS: find the account
$stmt = $pdo->prepare(
    'SELECT * FROM users WHERE email = ? LIMIT 1'
);
$stmt->execute([$email]);
$user = $stmt->fetch(PDO::FETCH_ASSOC);

// AUTH: verify + create session
if (!$user || !password_verify($password, $user['password'])) {
    // LOGS: audit failed login
    $log = $pdo->prepare(
        'INSERT INTO logs (event, message, created_at) VALUES (?, ?, NOW())'
    );
    $log->execute(['auth.login_failed', $email]);
    throw new RuntimeException('Invalid credentials');
}

session_regenerate_id(true);
$_SESSION['user_id'] = $user['id'];

// LOGS: audit successful login
$log = $pdo->prepare(
    'INSERT INTO logs (event, user_id, created_at) VALUES (?, ?, NOW())'
);
$log->execute(['auth.login', $user['id']]);

Your application manually connects user lookup, password verification, session handling and audit logging.

With Prefab

$auth = new AuthManager();

$result = $auth->attempt($email, $password);

if (!$result->success) {
    // Your app decides the response.
}

With Prefab Users and Prefab Logs available, Auth uses their compatible capabilities automatically. The developer uses Auth; Prefab handles the integration.

Users ── user_provider ──┐
                         ├──→ Auth
Logs  ── logger ─────────┘
Install it. Use it. Compatible modules make it better automatically.
STEP 1

Create the project

Goal: create an empty Composer app we can grow.

mkdir prefab-tutorial
cd prefab-tutorial
composer init
mkdir public
mkdir storage
composer require tihloh/prefab-routes

Create public/index.php:

<?php
require __DIR__ . '/../vendor/autoload.php';

Run:

php -S 127.0.0.1:8000 -t public
Checkpoint: keep the server running. We use this same application throughout.
STEP 2

Make your first route

Goal: answer a browser request.

<?php
require __DIR__ . '/../vendor/autoload.php';
use Tihloh\Prefab\Routes\RouteManager;
$routes = new RouteManager();
$routes->get('/', fn () => 'Hello Prefab!');
$result=$routes->dispatch();
if (is_string($result)) echo $result;

Try: open http://127.0.0.1:8000/.

Expected: Hello Prefab!. One Prefab block is already useful alone.
STEP 3

Connect a database

Goal: make a database resource available to later modules.

composer require tihloh/prefab-database
$pdo = new PDO(
 'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
 'root','',[PDO::ATTR_ERRMODE=>PDO::ERRMODE_EXCEPTION]
);
Rule: explicit resources win. Prefab discovery fills missing configuration when a compatible resource is available.
STEP 4

Add Users

Goal: manage users and make user lookup available to compatible modules.

composer require tihloh/prefab-users
use Tihloh\Prefab\Users\Services\UserManager;

$users = new UserManager([
    'database' => $pdo,
    'table' => 'users',
]);
Schema note: the current Users package expects the mapped table to exist. Self-schema creation is a feature we are adding for database-backed modules; the tutorial will only show it once the implementation exists.
That's enough here. Compatible modules can use the user capability when they need it; you do not manually connect Users to every consumer.
STEP 5

Create a user safely

Goal: validate browser data before handing it to Users.

composer require tihloh/prefab-input
use Tihloh\Prefab\Input\Input;
$result=Input::from($_POST)->process([
 'name'=>'trim|required|string|max:100',
 'email'=>'trim|lowercase|required|email',
 'password'=>'required|string|min:8',
]);
if ($result->fails()) { print_r($result->errors()); return; }
$users->create($result->validated());

Try: submit an invalid email, then a valid one. Only declared validated fields proceed.

STEP 6 · PREFAB HIGHLIGHT

Add login

Goal: authenticate without manually wiring Auth to Users.

composer require tihloh/prefab-auth
use Tihloh\Prefab\Auth\Services\AuthManager;

$auth = new AuthManager();
$result = $auth->attempt($email, $password);

What does Prefab handle?

Auth needs user lookup
   ↓
Prefab Users is available
   ↓
Auth uses its compatible user capability
   ↓
No manual provider wiring
Developer-facing rule: if Prefab can safely discover and configure something itself, the normal tutorial does not ask you to do it.
STEP 7

Protect features

Goal: separate identity from authorization.

composer require tihloh/prefab-permissions

Auth answers who the actor is. Permissions answers what that actor may do. Compatible identity information is shared without making every controller rebuild it.

STEP 8 · BETTER TOGETHER

Add audit logs

Goal: improve compatible modules with logging without adding audit INSERT statements around them.

composer require tihloh/prefab-logs
Logs ── logger ──┬─→ Auth
                  └─→ Users

Once the logging capability is available, compatible modules can use it automatically for their infrastructure events.

Growth without dependency: Auth worked before Logs existed. Adding Logs gives compatible modules another capability.
STEP 9

Upload files

Goal: validate with Input, store with Files.

composer require tihloh/prefab-files
Input → validates upload → UploadedFile → Files → stores it

Each block keeps one responsibility.

STEP 10

Add notifications

composer require tihloh/prefab-notifications

Use Notifications for notices inside the application. A user update should not automatically notify merely because the module is installed—that is a business decision.

STEP 11

Add email

composer require tihloh/prefab-messaging

Messaging owns outbound communication. Compatible Fluent Extensions are intended to make explicit actions concise:

$users->update($id,$data)
      ->notify()
      ->email();

Installed capability becomes available; your application chooses to use it.

STEP 12

Inspect when you need to debug

Normal application code should stay simple. Inspection belongs here because developers only need it when diagnosing integration.

print_r($auth->explain());
print_r($users->explain());

Inspection can show which compatible resources were resolved without requiring those internals in normal application code.

STEP 13

Production

composer install --no-dev --optimize-autoloader

Use OPcache, externalize secrets, disable public display-errors and log exceptions server-side.

Tutorial complete: you started with one block and progressively gained capabilities without adopting a full framework architecture.
GUIDE

Auto-Wiring

Internally, modules publish named capabilities and compatible consumers resolve what they are missing. This is implementation knowledge for developers who need to understand or override the defaults—not ceremony required in normal usage.

Database → Users → user_provider → Auth
Logs → logger ───────────────────→ Auth / Users
Auth → actor_provider ───────────→ compatible consumers
GUIDE

Fluent Extensions

Auto-Wiring handles infrastructure. Extensions expose optional explicit business actions from installed compatible modules.

$users->update($id,$data);           // Users
$users->update($id,$data)->notify(); // + Notifications
$users->update($id,$data)->email();  // + Messaging
GUIDE

Existing projects

Keep your tables, PDO, controllers, views and structure. Provide what already exists; Prefab handles compatible missing plumbing where it safely can.

GUIDE

Error handling

Prefab should fail as a library, not take over the host application. Validation returns errors; unresolved resources and ambiguous integration produce clear catchable exceptions.

try {
 $result=$auth->attempt($email,$password);
} catch (RuntimeException $e) {
 // Your app chooses HTML, JSON, redirect or logging.
}
