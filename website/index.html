TUTORIAL + REFERENCE

Learn Prefab from an empty folder.

This guide assumes only a basic understanding of plain PHP: variables, arrays, functions, classes, require, forms and simple database concepts. You do not need Laravel or another framework.

Beginner friendlyPlain PHPComposerModularReference included
What you will build: a small PHP application with routes, database access, users and groups, validation, login, permissions and audit logs, then learn how Files, Notifications and Messaging fit into the same architecture.

How to use this page

If you are new to Composer, start at Prerequisites and follow every checkpoint. Experienced PHP developers can jump directly to a module section. Commands marked Verify are useful whenever something does not work.

BEFORE PREFAB

Minimum prerequisites

You need a command line, PHP, Composer and a text editor. A database is needed when the tutorial reaches Users. Git is recommended but is not required just to run Prefab.

PHP 8.1+

Prefab Routes currently requires PHP 8.1 or newer.

Composer 2

Downloads packages and generates the PHP autoloader.

Editor

VS Code, PhpStorm, Notepad++ or any editor that saves plain PHP files.

Database

MariaDB/MySQL is easiest for this tutorial. PDO must be enabled.

Terminal

PowerShell/CMD on Windows, or a shell on Linux/macOS.

Basic PHP

You should recognize $variables, arrays, classes and require.

Verify your machine first

php -v
composer --version
php -m

Look for PDO and the driver you plan to use, normally pdo_mysql. If php or composer is “not recognized”, fix that before creating the project.

BEGINNER SETUP

Install PHP and Composer

Windows

If you already use XAMPP, Laragon or another PHP stack, you may use its PHP executable. Make sure its PHP directory is on your PATH so php -v works from a new terminal. Then install Composer and let its installer use that PHP executable.

Linux

sudo apt update
sudo apt install php-cli php-mysql php-mbstring php-xml unzip
php -v

Install Composer using the official Composer installer for your operating system, then verify with composer --version.

Do not continue with a broken CLI setup. The web server PHP and terminal PHP can be different installations. The php -v and php -m commands show what Composer and the built-in server will actually use.
IMPORTANT

Package availability and the “minimum-stability” error

The source repository can contain a Prefab module before Packagist has a stable release for it. In that situation this command:

composer require tihloh/prefab-routes

can report:

Could not find a version of package tihloh/prefab-routes
matching your minimum-stability (stable).

This does not mean PHP or Composer is broken. Composer is saying it cannot currently resolve a stable published version matching your project.

For normal users

Use the plain composer require command once that module has a stable Packagist release. The tutorial intentionally keeps stable installation as the normal path.

For development/testing before a stable release

Use an explicit development version only when you deliberately want unreleased code:

composer require tihloh/prefab-routes:dev-main
Development versions are not the beginner default. They can change without a stable release boundary. Once a stable version is published, return to the ordinary command.
PROJECT SETUP

Create the tutorial project

mkdir prefab-tutorial
cd prefab-tutorial
composer init

Composer asks several questions. For a local tutorial you can accept sensible defaults. When finished, the important file is composer.json.

mkdir public
mkdir storage

Install Routes. If no stable package is published yet, use the development command explained above instead.

composer require tihloh/prefab-routes

Create public/index.php:

<?php

declare(strict_types=1);

require __DIR__ . '/../vendor/autoload.php';

echo 'Prefab is loaded';

Start PHP's development server:

php -S 127.0.0.1:8000 -t public

Open http://127.0.0.1:8000. You should see Prefab is loaded.

Checkpoint: if this works, PHP, Composer, the generated vendor/ directory and Composer autoloading are all working.
MODULE 1

Routing

A route connects an HTTP method and URL path to PHP code. Without a router, plain PHP applications commonly grow into manual checks of $_SERVER['REQUEST_URI'].

Install

composer require tihloh/prefab-routes

Minimal use

<?php
require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Routes\RouteManager;

$routes = new RouteManager();
$routes->get('/', fn () => 'Home');
$routes->get('/hello', fn () => 'Hello Prefab!');

$result = $routes->dispatch();
if (is_string($result)) {
    echo $result;
}

Try both / and /hello. Prefab Routes is framework-independent; it does not require Users, Auth or Permissions.

MODULE 2

Database

Before adding Users, create a database named prefab_tutorial. Prefab modules can work with compatible shared database resources, while plain PDO remains a valid way to provide an existing connection.

composer require tihloh/prefab-database
$pdo = new PDO(
    'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
    'root',
    '',
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
);

Test before continuing

$pdo->query('SELECT 1');
echo 'Database OK';
Reference: Prefab modules prefer explicit module configuration first, then shared Prefab configuration/capabilities where compatible. You can therefore start with plain PDO and progressively adopt more Prefab modules.
MODULE 3

Users and simple Groups

Prefab Users owns user-management behavior and supports simple groups consisting of an ID, name, optional description and membership. Permissions are deliberately separate.

composer require tihloh/prefab-users
use Tihloh\Prefab\Users\Services\UserManager;

$users = new UserManager([
    'database' => $pdo,
    'table' => 'users',
]);

Typical user operations

$user = $users->find(1);
$all  = $users->all();

$result = $users->create([
    'name' => 'Demo User',
    'email' => 'demo@example.com',
    'password' => password_hash('secret123', PASSWORD_DEFAULT),
]);

Groups

$groups = $users->groups();
$group = $groups->create('Staff', 'Application staff');
$groups->addUser($userId, $group->id);
$groups->syncUserGroups($userId, [1, 2]);

When Prefab Permissions is also installed, it can use the same logical group system and add authorization information rather than creating a second unrelated group concept.

MODULE 4

Input and validation

Never pass arbitrary browser input directly into user management or SQL. Validate and normalize it first.

composer require tihloh/prefab-input
use Tihloh\Prefab\Input\Input;

$result = Input::from($_POST)->process([
    'name' => 'trim|required|string|max:100',
    'email' => 'trim|lowercase|required|email',
    'password' => 'required|string|min:8',
]);

if ($result->fails()) {
    print_r($result->errors());
    return;
}

$users->create($result->validated());

The application still controls whether errors become HTML, JSON, a redirect or something else.

MODULE 5

Authentication

Authentication answers who is signed in? Prefab Auth can consume the user capability exposed by Prefab Users when both are present.

composer require tihloh/prefab-auth
use Tihloh\Prefab\Auth\Services\AuthManager;

$auth = new AuthManager();
$result = $auth->attempt($email, $password);

if (!$result->success) {
    echo 'Invalid login';
}

You do not need to call an internal configuration method just because Prefab can resolve compatible installed modules itself.

MODULE 6

Permissions

Permissions answers what may this user do? This remains independent from user identity.

composer require tihloh/prefab-permissions

Permission definitions contain the complete metadata. User/group overrides stay lightweight: permission ID plus allow/deny value. A missing override means inherit.

User override
   ↓ none
Group overrides
   ↓ none
Permission default
   ↓
Allow / Deny

Prefab Users can supply the simple groups; Permissions upgrades those same groups with authorization behavior. Permissions can also work without Prefab Users for projects that already have their own user system.

MODULE 7

Audit Logs

composer require tihloh/prefab-logs

Logs is independent, but compatible modules can publish meaningful infrastructure events to it. This avoids scattering manual audit INSERT statements around Auth, Users and Permissions.

Users ── user_provider ──┐
                         ├──→ Auth
Logs  ── logger ─────────┘

Users + Permissions + Logs
       ↓
user/group changes and authorization events can share audit infrastructure
Important: installing Logs should enhance compatible infrastructure behavior, not invent application business events you never requested.
MODULE 8

Files

composer require tihloh/prefab-files

Use Input to validate incoming upload data and Files to store/manage the file. Keep validation and storage as separate responsibilities.

MODULE 9

Notifications

composer require tihloh/prefab-notifications

Notifications represents application notices. Installing it does not mean every user update should automatically generate a notice; that remains an explicit business decision.

MODULE 10

Messaging

composer require tihloh/prefab-messaging

Messaging owns outbound communication such as email. It can cooperate with other modules while remaining independently usable.

REFERENCE

Shared Prefab configuration

Use shared configuration for values that genuinely belong to the whole application, such as the common database or application identity. Module-specific configuration should remain possible when a module needs an override.

use Tihloh\Prefab\PrefabConfig;

PrefabConfig::set([
    'name' => 'my_app',
    'database' => $pdo,
]);

The goal is fewer repeated settings, not hidden magic. Explicit module configuration should still win when supplied.

REFERENCE

Session isolation is mandatory

PHP applications hosted under the same domain can otherwise collide through the same session cookie. For example, localhost/web1 and localhost/web2 must not accidentally become one application's session.

Prefab's session-aware modules should derive an isolated application namespace from the configured Prefab application name by default. A simpler explicit namespace can be supplied when the application name is unsuitable.

PrefabConfig::set([
    'name' => 'web1',
]);

If no session-specific configuration is provided, isolation should still be the safe default rather than silently sharing a generic PHP session across neighboring applications.

REFERENCE

How Auto-Wiring works

Prefab modules remain independently installable. When compatible modules exist in the same application, they publish and consume small capabilities.

Database ───────────────→ shared database capability
Users ── user_provider ─→ Auth
Users ── group_provider ─→ Permissions
Logs  ── logger ────────→ compatible modules
Auth  ── actor_provider ─→ compatible modules

Auto-wiring handles compatible infrastructure. It should not make business decisions for your application.

REFERENCE

Troubleshooting

Package cannot be found / minimum-stability

Check whether a stable package version has actually been published. During development only, explicitly request :dev-main.

Class not found

composer dump-autoload
composer show

Confirm vendor/autoload.php is required and that the package appears in composer show.

PDO driver missing

php -m

Enable/install the PDO driver matching your database.

Port 8000 already in use

php -S 127.0.0.1:8001 -t public

Need to inspect Prefab resolution

print_r($users->explain());
print_r($auth->explain());

Use inspection for debugging; normal application code should not need to manually reproduce Prefab's internal capability wiring.

REFERENCE

Production checklist

composer install --no-dev --optimize-autoloader

Use a real web server, enable OPcache, keep credentials outside public source files, use HTTPS, disable public PHP error display, log exceptions server-side, use secure session cookie settings, restrict writable directories, back up the database, and pin/test dependency updates before deployment.
