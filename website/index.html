Without Prefab vs. With Prefab

Imagine a login that needs Users + Authentication + Activity Logging.

Without Prefab

session_start();

$stmt = $pdo->prepare(
  'SELECT * FROM users WHERE email = ? LIMIT 1'
);
$stmt->execute([$_POST['email']]);
$user = $stmt->fetch(PDO::FETCH_ASSOC);

if (!$user || !password_verify(
    $_POST['password'], $user['password'])) {
    throw new RuntimeException('Invalid credentials.');
}

session_regenerate_id(true);
$_SESSION['user_id'] = $user['id'];

$stmt = $pdo->prepare(
  'INSERT INTO logs (user_id, action, created_at)
   VALUES (?, ?, NOW())'
);
$stmt->execute([$user['id'], 'auth.login']);

With Prefab

$result = $auth->login([
    'email'    => $_POST['email'],
    'password' => $_POST['password'],
]);

if (!$result->ok()) {
    // Show your application's error.
}
Users→Auth→Logs

Prefab handles reusable infrastructure. Your application still decides what happens next.

INITIAL SETUP

Start with only what you need

Prefab has no required Core package. Install one block or combine compatible blocks.

composer require tihloh/prefab-routes

Composer provides autoloading as usual:

require __DIR__ . '/vendor/autoload.php';
BASIC · STEP 1

Routes

Start with request routing. A small application can use Routes by itself.

$routes = new RouteManager();
$routes->get('/', fn () => 'Hello Prefab');
$routes->get('/users/{id}', 'UserController@show');
$routes->dispatch();
BASIC · STEP 2

Input

Add structured input processing and validation when your application begins accepting data.

$input->validate([
    'email' => 'required|email',
    'age'   => 'required|integer|min:18',
]);
BASIC · STEP 3

Database

Use Prefab Database when you want lightweight database infrastructure, or keep your existing PDO connection.

BASIC · STEP 4

Users

Map Prefab Users to your existing users, employees or accounts table instead of replacing your schema.

$user = $users->find(25);
$users->update(25, $data);
BUILD AN APP · STEP 5

Authentication

Add Auth when the application needs login, logout and a current authenticated actor.

$result = $auth->login($credentials);
BUILD AN APP · STEP 6

Permissions

Authentication answers who the user is. Permissions answers what that user may do.

Logs

Add audit and activity history. Compatible infrastructure such as authentication can expose meaningful events to Logs.

COMMUNICATION · STEP 9

Notifications

Use Notifications for notices that live inside the application: bell items, inbox notices and read state.

COMMUNICATION · STEP 10

Messaging

Use Messaging for communication leaving the application, such as email.

BETTER TOGETHER

Modules improve each other

Users                 → user management
Users + Auth          → authentication
Users + Auth + Logs   → authentication + auditing

Each block remains useful alone. Compatible blocks can provide more value together.

Auto-Wiring

Prefab can connect compatible infrastructure when the relationship is natural. Explicit configuration always wins.

Users ── user provider ──→ Auth
Auth  ── current actor ──→ Permissions / Logs

Fluent Extensions

Optional modules can add explicit capabilities without being hard-coded into the module they enhance.

$users->update($id, $data)
      ->notify()
      ->email();

Installing Messaging should not silently email every changed user. Business decisions remain explicit.

ADVANCED

Configuration

Small systems configure modules directly. Larger systems can share configuration while retaining explicit overrides.

Diagnostics

$auth->explain();
$info = PrefabRuntime::inspect();

Automatic behavior should be inspectable, not mysterious.

Error Handling

Prefab libraries should return documented results or throw clear, catchable exceptions. They should not unexpectedly terminate the host application.

Production

Keep the same Composer workflow in production. Optimize Composer autoloading and PHP OPcache as appropriate for your server.
