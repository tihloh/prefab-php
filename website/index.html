INTRODUCTION

Reusable PHP building blocks without adopting a full framework.

Prefab PHP is a family of small, framework-independent Composer packages for common application features such as routing, users, authentication, permissions, logs, files and messaging.

ModularReusableIndependentAdaptiveBetter Together
Prefab is not a framework. It does not take ownership of your project structure, controllers, templates or business logic. Install only the modules you need and keep writing normal PHP.

The idea

Each module is useful by itself. When compatible Prefab modules are installed together, they can discover shared capabilities and remove repetitive integration code.

Small project
    ↓
Install one module
    ↓
Use it directly

Project grows
    ↓
Install another compatible module
    ↓
Prefab connects compatible infrastructure automatically

This tutorial is written for developers who already know basic plain PHP—variables, arrays, functions, classes, forms and simple database concepts—but it does not assume Laravel, Symfony or expert-level Composer knowledge.

Windows and Linux are both first-class tutorial paths. When commands differ, this guide shows separate PowerShell and Linux shell examples. When the command is identical, it is shown once as a common command.
WHY PREFAB?

With Prefab vs without Prefab

A normal login already crosses at least three concerns: Users, Authentication and Logging.

Without Prefab

// USERS: find account
$stmt = $pdo->prepare(
    'SELECT * FROM users WHERE email = ? LIMIT 1'
);
$stmt->execute([$email]);
$user = $stmt->fetch(PDO::FETCH_ASSOC);

// AUTH: verify password
if (!$user || !password_verify($password, $user['password'])) {
    // LOGS: manually record failure
    $log = $pdo->prepare(
        'INSERT INTO logs (event, message, created_at) VALUES (?, ?, NOW())'
    );
    $log->execute(['auth.login_failed', $email]);
    throw new RuntimeException('Invalid credentials');
}

// AUTH: manually manage session
session_regenerate_id(true);
$_SESSION['user_id'] = $user['id'];

// LOGS: manually record success
$log = $pdo->prepare(
    'INSERT INTO logs (event, user_id, created_at) VALUES (?, ?, NOW())'
);
$log->execute(['auth.login', $user['id']]);

Your application manually coordinates user lookup, password verification, session state and audit logging.

With Prefab

use Tihloh\Prefab\Auth\Services\AuthManager;

$auth = new AuthManager();
$result = $auth->attempt($email, $password);

if (!$result->success) {
    // Your app decides the response.
}

If Prefab Users and Prefab Logs are available, Auth can use their compatible capabilities without making your controller manually wire them together.

Users ── user_provider ──┐
                         ├──→ Auth
Logs  ── logger ─────────┘
Install it. Use it. Compatible modules make the application better without forcing a new architecture.
CORE CONCEPT

How Prefab works

Independent modules

Routes does not require Users. Users does not require Auth. Permissions can work with Prefab Users or another user system.

Capabilities

A module can publish reusable infrastructure such as a database, user provider, logger, group provider or current actor.

Auto-discovery

Compatible consumers can discover a capability instead of asking the developer to repeat obvious wiring.

Explicit still wins

If you provide a module-specific configuration or adapter, Prefab should respect it before automatic defaults.

No hidden business decisions

Infrastructure may auto-connect; your application's business actions remain explicit.

Framework-independent

Plain PHP is the baseline. Laravel or other frameworks can integrate through adapters instead of becoming hard dependencies.

Explicit module configuration
          ↓
Shared Prefab configuration
          ↓
Compatible discovered capability
          ↓
Safe internal default
          ↓
Clear error if required resource is unavailable
BEFORE PREFAB

Minimum prerequisites

You need PHP 8.1 or newer, Composer 2, a terminal and a text editor. Database-backed sections need PDO plus a database driver such as pdo_mysql.

PHP 8.1+

Required by current Prefab packages.

Composer 2

Installs packages and creates the autoloader.

Editor

VS Code, PhpStorm, Notepad++ or another PHP-capable editor.

PDO

Required when using database-backed modules.

MariaDB/MySQL

Used by examples; another supported PDO database may also work.

Basic PHP

Know variables, arrays, functions, classes, forms and require.

Verify before continuing

These commands are the same on Windows and Linux:

php -v
composer --version
php -m

Confirm PDO appears. For MySQL/MariaDB, also look for pdo_mysql.

BEGINNER SETUP

Install PHP and Composer

Windows

PowerShell / Windows

If you already use XAMPP, Laragon or another PHP stack, you may use its PHP executable. The important requirement is that PHP works from a new PowerShell window.

php -v
where.exe php

If php is not recognized, add the PHP directory to your Windows PATH, close PowerShell, open it again and retry.

Install Composer for Windows, point it at the PHP executable you verified, then check:

composer --version
where.exe composer

For MySQL support:

php -m | findstr /I "PDO pdo_mysql"
Linux

Ubuntu / Debian

sudo apt update
sudo apt install php-cli php-mysql php-mbstring php-xml unzip curl
php -v
which php

Install Composer using the official Composer installer or your distribution's supported Composer package, then verify:

composer --version
which composer
php -m | grep -Ei 'PDO|pdo_mysql'
CLI PHP matters. The PHP used by Apache/Nginx can be different from the PHP used by Composer and php -S. Always verify the terminal version first.
IMPORTANT

Package availability and minimum-stability

Source code can exist in the Prefab repository before a stable Packagist release exists. If Composer says:

Could not find a version of package tihloh/prefab-routes
matching your minimum-stability (stable).

Composer itself may be working correctly—it simply cannot resolve a stable published version.

Stable release

composer require tihloh/prefab-routes

Development/testing before stable release

composer require tihloh/prefab-routes:dev-main
Use :dev-main only when deliberately testing unreleased code. Stable packages should use the normal command.

MODULE 1

Routing

A route maps an HTTP method and URL path to PHP code.

composer require tihloh/prefab-routes
<?php
require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Routes\RouteManager;

$routes = new RouteManager();
$routes->get('/', fn () => 'Home');
$routes->get('/hello', fn () => 'Hello Prefab!');

$result = $routes->dispatch();
if (is_string($result)) echo $result;

Visit / and /hello. Routes works independently; Auth and Users are not required.

MODULE 2

Database

Create a database called prefab_tutorial using your preferred database administration tool or CLI.

composer require tihloh/prefab-database
$pdo = new PDO(
    'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
    'root',
    '',
    [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
);

$pdo->query('SELECT 1');
Windows and Linux use the same PHP/PDO code. Only your database service installation and credentials may differ.
MODULE 3

Users and simple Groups

Prefab Users handles user management and simple group organization. A basic group contains an ID, name, optional description and user membership—no permissions are required.

composer require tihloh/prefab-users
use Tihloh\Prefab\Users\Services\UserManager;

$users = new UserManager([
    'database' => $pdo,
    'table' => 'users',
]);

$user = $users->find(1);
$all  = $users->all();

Groups

$groups = $users->groups();
$staff = $groups->create('Staff', 'Application staff');
$groups->addUser($userId, $staff->id);
$groups->syncUserGroups($userId, [1, 2]);

When Prefab Permissions is added later, it can upgrade these same logical groups with authorization instead of introducing a second disconnected group system.

MODULE 4

Input and validation

composer require tihloh/prefab-input
use Tihloh\Prefab\Input\Input;

$result = Input::from($_POST)->process([
    'name' => 'trim|required|string|max:100',
    'email' => 'trim|lowercase|required|email',
    'password' => 'required|string|min:8',
]);

if ($result->fails()) {
    print_r($result->errors());
    return;
}

$users->create($result->validated());

The module validates data; your application still decides whether errors become HTML, JSON or redirects.

MODULE 5

Authentication

Auth answers: Who is signed in?

composer require tihloh/prefab-auth
use Tihloh\Prefab\Auth\Services\AuthManager;

$auth = new AuthManager();
$result = $auth->attempt($email, $password);

if (!$result->success) {
    echo 'Invalid login';
}

If Prefab Users is installed and compatible, Auth can use its user capability automatically. Normal application code should not need to call internal auto-configuration methods.

MODULE 6

Permissions

Permissions answers: What may this user do?

composer require tihloh/prefab-permissions
User override
   ↓ none
Group overrides
   ↓ none
Permission definition default
   ↓
Allow / Deny

Permission definitions contain metadata. User and group records keep only permission IDs and allow/deny values. Missing override means inherit.

With Prefab Users installed, Permissions can use the same groups. Without Prefab Users, Permissions can manage authorization groups for another user system.

MODULE 7

Audit Logs

Compatible modules can publish meaningful infrastructure events to Prefab Logs instead of requiring manual audit SQL around every operation.

REFERENCE

Shared Prefab configuration

use Tihloh\Prefab\PrefabConfig;

PrefabConfig::set([
    'name' => 'my_app',
    'database' => $pdo,
]);

Shared configuration is for values that genuinely belong to the whole application. Explicit module configuration should override it when supplied.

REFERENCE

Session isolation is mandatory

Every Prefab application should receive an isolated session identity even when it is the only application on the server.

localhost/web1 → isolated Prefab session
localhost/web2 → different isolated Prefab session

If no session namespace is configured, Prefab derives one automatically from application/deployment context. Developers may explicitly use the same namespace when intentional sharing is required.

PrefabConfig::set([
    'session' => [
        'namespace' => 'company_sso',
    ],
]);

No separate shared=true flag is necessary; using the same explicit namespace is itself the intent.

REFERENCE

Auto-Wiring

Database ───────────────┐
Users → user_provider ──┼─→ compatible modules
Users → group_provider ─┤
Logs  → logger ─────────┤
Auth  → actor_provider ─┘

Auto-wiring is infrastructure behavior. It should reduce repetitive setup without making business behavior implicit.

Production checklist

composer install --no-dev --optimize-autoloader
HTTPS

Serve authentication and sensitive data over TLS.

Secrets

Keep database passwords and API credentials outside public source files.

Errors

Disable public error display and log errors server-side.

OPcache

Enable PHP OPcache on production servers.

Sessions

Use secure cookie settings and Prefab application isolation.

Permissions

Authentication is not authorization; enforce permissions where required.
