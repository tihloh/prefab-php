START HERE

Learn Prefab by building with it.

This tutorial starts with ordinary PHP, shows the plumbing you normally write yourself, then adds Prefab one independent block at a time until the pieces begin working together.

ModularReusableIndependentAdaptiveBetter Together
What Prefab is: a modular PHP application toolkit. It is not a full-stack framework and does not require you to adopt a project skeleton, ORM, base controller or special application lifecycle.
WHY PREFAB?

Without Prefab vs. with Prefab

Imagine a login that needs three common concerns: Users + Authentication + Activity Logging.

Without Prefab

session_start();

$stmt = $pdo->prepare(
    'SELECT * FROM users WHERE email = ? LIMIT 1'
);
$stmt->execute([$_POST['email']]);
$user = $stmt->fetch(PDO::FETCH_ASSOC);

if (!$user || !password_verify(
    $_POST['password'],
    $user['password']
)) {
    throw new RuntimeException('Invalid credentials.');
}

session_regenerate_id(true);
$_SESSION['user_id'] = $user['id'];

$stmt = $pdo->prepare(
    'INSERT INTO logs (user_id, action, created_at)
     VALUES (?, ?, NOW())'
);
$stmt->execute([$user['id'], 'auth.login']);

This is valid PHP, but your application owns user lookup, password verification, session management, logging and all the glue between them.

With Prefab

$result = $auth->attempt(
    $_POST['email'] ?? '',
    $_POST['password'] ?? ''
);

if (!$result->success) {
    // Your application decides the response.
}
Users→Auth→Logs

Each module owns one reusable concern. Your application still owns its business decisions and presentation.

You decide what the application does. Prefab handles reusable plumbing.

The important difference is not only line count. The application can keep its own users table, PDO connection, controllers, views and deployment model while replacing repetitive infrastructure gradually.

BEFORE YOU BEGIN

Requirements

The current Prefab packages target PHP 8.1 or newer. Composer is the normal installation method. Some modules have additional PHP extension requirements.

Core

PHP 8.1+ and Composer.

Database

PDO plus the driver for MySQL/MariaDB, PostgreSQL, SQLite or SQL Server.

Input / Files

ext-fileinfo for MIME detection.

php -v
composer --version
INITIAL SETUP

Start with only what you need

There is no required prefab-core. For this tutorial we will gradually install modules, beginning with Routes:

composer require tihloh/prefab-routes

Composer creates or updates composer.json and installs the package in vendor/. Load Composer once in your application entry point:

<?php

require __DIR__ . '/../vendor/autoload.php';
Existing project? Keep your current structure. Prefab does not require the directory layout shown below; it is only the tutorial layout.
TUTORIAL PROJECT

A tiny application we can grow

We will use a simple user-management application and grow it throughout the tutorial.

my-app/
├── public/
│   └── index.php
├── src/
│   └── Controllers/
├── storage/
├── composer.json
└── vendor/

Run PHP's development server from the project root while learning:

php -S 127.0.0.1:8000 -t public

Then open http://127.0.0.1:8000.

BASIC · STEP 1

Routes — give requests a destination

Install:

composer require tihloh/prefab-routes

Create public/index.php:

<?php

require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Routes\RouteManager;

$routes = new RouteManager();

$routes->get('/', fn () => 'Home');
$routes->get('/about', fn () => 'About');
$routes->get('/hello/{name}', fn (string $name) => "Hello {$name}");

$result = $routes->dispatch();

if (is_string($result)) {
    echo $result;
}

Now:

GET /              → Home
GET /about         → About
GET /hello/Chris   → Hello Chris

Controller handlers

Prefab supports both compact controller strings and native PHP callable arrays:

$routes->get('/users/{id}', 'UserController@show');

// or
use App\Controllers\UserController;
$routes->get('/users/{id}', [UserController::class, 'show']);

For compact strings, configure the controller namespace once:

$routes = new RouteManager([
    'controller_namespace' => 'App\\Controllers',
]);

Parameters and constraints

$routes->get('/users/{id}', 'UserController@show')
    ->where('id', '\\d+');

/users/25 matches. /users/chris does not.

Named routes and URL generation

$routes->get('/users/{id}', 'UserController@show')
    ->name('users.show');

$url = $routes->url('users.show', ['id' => 25]);
// /users/25

Groups

$routes->group('/admin', function (RouteManager $routes) {
    $routes->get('/users', 'UserController@index');
    $routes->get('/logs', 'LogController@index');
});

The routes become /admin/users and /admin/logs.

You now have: request routing without adopting a framework. Next we will safely process submitted data.
BASIC · STEP 2

Input — turn raw input into application data

composer require tihloh/prefab-input

Raw $_POST data is untrusted. Prefab Input lets you define exactly what fields the application accepts, normalize them, cast types and validate them in one pipeline.

use Tihloh\Prefab\Input\Input;

$result = Input::from($_POST)->process([
    'name'   => 'trim|required|string|max:100',
    'email'  => 'trim|lowercase|required|email',
    'age'    => 'nullable|integer|min:18',
    'active' => 'default:true|boolean',
]);

if ($result->fails()) {
    print_r($result->errors());
    return;
}

$data = $result->validated();

If the browser sends extra fields such as role=admin but the schema does not declare role, that field does not enter validated().

What the pipeline can do

"  Christian  "  → "Christian"
"USER@MAIL.COM"  → "user@mail.com"
"25"             → 25
"true"           → true
""               → null

Compact rules can also be written as arrays:

'name' => [
    'trim',
    'required',
    'string',
    'max:100',
]
Boundary: Input decides whether incoming data is acceptable. It does not store users or files permanently.
BASIC · STEP 3

Database — optional shared database infrastructure

composer require tihloh/prefab-database

Prefab Database is optional. You may keep using PDO directly. Install it when named connections and a lightweight query API make the application clearer.

use Tihloh\Prefab\Database\Services\DatabaseManager;

$database = new DatabaseManager([
    'connections' => [
        'main' => [
            'driver'   => 'mysql',
            'host'     => '127.0.0.1',
            'database' => 'app',
            'username' => 'app',
            'password' => 'secret',
        ],
    ],
]);

$users = $database
    ->table('users')
    ->where('active', true)
    ->get();

Already have PDO? Keep it:

$pdo = new PDO($dsn, $username, $password);

$database = new DatabaseManager([
    'connections' => [
        'main' => $pdo,
    ],
]);
Important: Prefab Database is not an ORM. It intentionally stays close to PDO and SQL.
BASIC · STEP 4

Users — keep your existing user table

composer require tihloh/prefab-users

Suppose your project already has an employees table instead of a conventional users table:

employees
├── employee_id
├── full_name
├── email_address
├── is_active
├── office_name
└── position_title

Map it rather than redesigning it:

use Tihloh\Prefab\Users\Mapping\UserMap;
use Tihloh\Prefab\Users\Repositories\PdoUserProvider;
use Tihloh\Prefab\Users\Services\UserManager;

$map = new UserMap(
    table: 'employees',
    id: 'employee_id',
    name: 'full_name',
    email: 'email_address',
    active: 'is_active',
    attributes: [
        'office' => 'office_name',
        'position' => 'position_title',
    ],
    allowDelete: false,
);

$users = new UserManager(
    new PdoUserProvider($pdo, $map),
);

$user = $users->find(25);

Common operations

$users->all();
$users->find(25);
$users->findByEmail('user@example.com');
$users->create([...]);
$users->update(25, [...]);
$users->delete(25);

At this point Users is useful completely by itself. Auth is not required.

BUILD AN APP · STEP 5

Authentication — establish who the current user is

composer require tihloh/prefab-auth

Auth does not own your user table. It accepts a compatible user provider and a replaceable session store.

use Tihloh\Prefab\Auth\Services\AuthManager;
use Tihloh\Prefab\Auth\Session\NativeSessionStore;

$auth = new AuthManager(
    $userProvider,
    new NativeSessionStore(),
);

Attempt a login:

$result = $auth->attempt(
    $_POST['identifier'] ?? '',
    $_POST['password'] ?? '',
    [
        'ip_address' => $_SERVER['REMOTE_ADDR'] ?? null,
        'user_agent' => $_SERVER['HTTP_USER_AGENT'] ?? null,
    ],
);

if ($result->success) {
    header('Location: /dashboard');
    exit;
}

Prefab returns an authentication result. It does not decide whether your application should redirect, return JSON or render HTML.

Current user

$auth->check();
$auth->id();
$auth->user();
$auth->logout();
if ($auth->check()) {
    echo 'Welcome ' . $auth->user()->name;
}
You now have: Users describing project-owned users and Auth handling authentication without requiring a new user schema.
BUILD AN APP · STEP 6

Permissions — decide what a user may do

composer require tihloh/prefab-permissions

Authentication answers Who are you? Permissions answers What may you do?

Prefab resolves permissions through three levels:

User override
     ↓
Group permission
     ↓
Definition default

Configure permission definitions:

$permissions = new PermissionManager([
    'definitions' => __DIR__ . '/config/permissions.php',
]);

Then application code asks one stable question:

if ($permissions->can($user, 'documents.approve')) {
    // Allowed.
}

Explicit user override:

$permissions->set(
    'user',
    $userId,
    'documents.approve',
    true,
);

Restore inheritance:

$permissions->clear(
    'user',
    $userId,
    'documents.approve',
);
Tri-state: allow, deny and inherit are intentionally different. Clearing an override means “let the lower level decide,” not “deny.”
BUILD AN APP · STEP 7

Files — safely store and retrieve application files

composer require tihloh/prefab-files

For a small application, one root is enough:

use Tihloh\Prefab\Files\FileManager;

$files = new FileManager([
    'root' => __DIR__ . '/../storage',
]);

$files->put(
    'documents/report.txt',
    'Hello Prefab',
);

$content = $files->read('documents/report.txt');

Named disks

$files = new FileManager([
    'default' => 'private',
    'disks' => [
        'private' => [
            'driver' => 'local',
            'root' => __DIR__ . '/../storage/private',
        ],
        'public' => [
            'driver' => 'local',
            'root' => __DIR__ . '/../public/uploads',
            'url' => '/uploads',
        ],
    ],
]);

$files->put('avatars/user.jpg', $contents, 'public');

Paths stay relative to the selected disk. Traversal attempts such as ../../.env are rejected.

Input decides whether an uploaded file is acceptable. Files decides where and how it is stored.
BUILD AN APP · STEP 8

Logs — store structured activity and audit history

composer require tihloh/prefab-logs
use Tihloh\Prefab\Logs\Repositories\PdoLogRepository;
use Tihloh\Prefab\Logs\Services\LogManager;

$logs = new LogManager(
    new PdoLogRepository($pdo),
);

$logs->record([
    'action' => 'user.updated',
    'subject_type' => 'user',
    'subject_id' => 25,
    'actor_id' => 7,
    'message' => 'User profile was updated.',
]);

Prefer structured events when possible:

$logs->record([
    'action' => 'user.updated',
    'subject_type' => 'user',
    'subject_id' => 25,
    'actor_id' => 7,
    'changes' => [
        'office' => [
            'old' => 'Accounting',
            'new' => 'Budget',
        ],
    ],
    'metadata' => [
        'source' => 'admin-ui',
    ],
]);

Actor is who performed the operation. Subject is what the operation affected.

COMMUNICATION · STEP 9

Notifications — internal application notices

composer require tihloh/prefab-notifications
use Tihloh\Prefab\Notifications\NotificationManager;

$notifications = new NotificationManager();

$notification = $notifications->send(
    25,
    'Document Approved',
    'OBR-2026-001 has been approved.',
    ['document_id' => 1001],
    '/documents/1001',
);

Read state is part of this module:

$recent = $notifications->recent(25);
$unread = $notifications->unread(25);
$count = $notifications->unreadCount(25);

$notifications->markRead($notification->id);
$notifications->markUnread($notification->id);
$notifications->delete($notification->id);

The default store is in-memory. Persistent applications can use PdoNotificationStore.

Boundary: Notifications are internal bell/inbox notices. Email, SMS and other external delivery belong to Messaging.
COMMUNICATION · STEP 10

Messaging — send information outside the application

composer require tihloh/prefab-messaging

The simplest mail operation is intentionally small:

$result = $messaging->mail(
    'user@example.com',
    'Annual Report',
    'Your report is ready.',
);

SMTP

$smtp = new SmtpTransport([
    'host' => 'smtp.example.com',
    'port' => 587,
    'username' => 'user@example.com',
    'password' => 'secret',
    'encryption' => 'tls',
    'from' => [
        'address' => 'noreply@example.com',
        'name' => 'My System',
    ],
]);

$messaging = new MessagingManager([
    new MailChannel($smtp),
]);

Attachments

$message = new Message(
    subject: 'Report',
    text: 'Your report is attached.',
    attachments: [
        Attachment::fromPath('/tmp/report.pdf'),
    ],
);

Templates

$template = new Template(
    subject: 'Hello {{name}}',
    text: 'Your report {{report}} is ready.'
);

$message = $template->render([
    'name' => 'Demo User',
    'report' => 'AR-2026',
]);

Every delivery returns a DeliveryResult so the application can decide what to do with success or failure.

BETTER TOGETHER

Users + Auth + Logs

Now compare the responsibilities:

Users  → where/how project users are represented
Auth   → authentication and current session
Logs   → structured audit/activity history

Auth can work with a compatible user provider instead of owning user storage. Authentication results can expose structured log data:

$result = $auth->attempt($identifier, $password);

if ($result->success) {
    $logs?->record($result->log);
}

This is the safe baseline even without automatic wiring: the modules are interoperable without hard dependencies.

Prefab direction: where an infrastructure relationship is unambiguous, Auto-Wiring can remove this glue when compatible capabilities are registered. Explicit configuration remains stronger.
BETTER TOGETHER

Routes + Auth + Permissions

Routing decides where a request goes. Authentication and Permissions decide whether the current actor is allowed to reach protected application behavior.

Prefab Routes supports reusable middleware today:

$routes->middleware('auth', function (callable $next, $match) use ($auth) {
    if (!$auth->check()) {
        http_response_code(401);
        return 'Unauthorized';
    }

    return $next();
});

$routes->get('/profile', 'ProfileController@index')
    ->middleware('auth');

Groups keep repeated access rules compact:

$routes->group([
    'prefix' => '/admin',
    'middleware' => ['auth'],
], function (RouteManager $routes) {
    $routes->get('/users', 'UserController@index');
    $routes->get('/logs', 'LogController@index');
});
Fluent integration direction: helpers such as route auth(), can() and validate() are intended to become richer when the corresponding modules are installed, while Routes remains standalone.
BETTER TOGETHER

Input + Files

This boundary is deliberately clean:

multipart request
      ↓
Prefab Input
validate / normalize UploadedFile
      ↓
Prefab Files
choose disk / path / collision policy
      ↓
stored file

That means Input does not become a storage library, and Files does not become a request validator.

ADVANCED INTEGRATION

Auto-Wiring — connect infrastructure without hiding policy

Prefab modules can register capabilities with the shared runtime. Compatible modules can discover those capabilities when a direct configuration value was not supplied.

Explicit module configuration
        ↓
Module-specific PrefabConfig
        ↓
Common PrefabConfig
        ↓
Compatible discovered capability
        ↓
Internal default
        ↓
Clear error if still unresolved
Explicit configuration wins. Auto-Wiring fills the gaps.

Good Auto-Wiring examples are infrastructure relationships such as a database capability, current actor provider or logger. Prefab should not automatically invent business actions such as emailing a user after every update.

ADVANCED INTEGRATION

Fluent Extensions — add capabilities without hard package dependencies

A provider module can register a method on a compatible Prefab object. This allows the assembled application to become more expressive as modules are added.

$users->update($id, $data)
      ->notify()
      ->email();

The intended ownership rule is important:

Notifications owns ->notify()
Messaging     owns ->email()
Logs          owns ->audit()

Users should not contain Messaging code merely to expose email().

Optional capabilities can be inspected:

$operation->hasExtension('notify');
$operation->extensions();

$info = PrefabRuntime::inspect();
$info['extensions'];
Version note: Prefab's extension architecture is still evolving. Treat module READMEs and released package versions as the source of truth for which concrete extensions are currently implemented.
ADVANCED

Configuration — simple locally, shared when useful

A small system should usually configure each module directly. Larger systems can use shared Prefab configuration and capability discovery.

1. Direct module configuration       ← strongest
2. Module-specific PrefabConfig
3. Common PrefabConfig
4. Compatible Auto-Wired capability
5. Module default
6. Clear resolution error

This order prevents “magic” from overriding application intent.

ADVANCED

Diagnostics — understand what Prefab assembled

Automatic behavior must be inspectable.

$auth->explain();
$users->explain();

$info = PrefabRuntime::inspect();

The runtime inspection can expose registered modules, capability providers, fluent extensions and resolution decisions without exposing secret connection values.

ADVANCED

Error handling — the host application stays in control

Prefab libraries should not unexpectedly die() or exit() for ordinary failures. The application decides how an error becomes HTML, JSON, a redirect or a log entry.

Invalid submitted data       → validation result/errors
Authentication failure       → authentication result
Delivery failure             → DeliveryResult / documented failure
Missing required resource    → clear exception
Missing optional extension   → BadMethodCallException
Ambiguous integration        → RuntimeException with details

Typical pattern:

try {
    // Prefab operation
} catch (Throwable $e) {
    // Log, render, return JSON, or convert to your app's error model.
}
ADVANCED

Production — nothing special is required

Prefab remains ordinary PHP installed by Composer. A normal production deployment can use:

composer install --no-dev --optimize-autoloader

Enable and configure PHP OPcache according to your hosting environment. Prefab does not require a daemon, Node.js runtime, proprietary binary or custom PHP extension.

Deployment principle: installing Prefab should add application capability, not a new infrastructure platform that every project must operate.
