Audit Logs

Audit logs answer questions such as “who changed this record?”, “what changed?”, and “when did it happen?” This tutorial records real events, stores them in the database and then queries them by actor and subject.

1. Install Logs

composer require tihloh/prefab-logs

Prefab Logs separates the logging API from storage. LogManager is what application code calls. PdoLogRepository is the database-backed repository used in this tutorial.

2. Connect the log repository

Create public/logs.php:

<?php
require __DIR__ . '/../vendor/autoload.php';

use Tihloh\Prefab\Logs\Repositories\PdoLogRepository;
use Tihloh\Prefab\Logs\Services\LogManager;

$pdo = new PDO(
    'mysql:host=127.0.0.1;dbname=prefab_tutorial;charset=utf8mb4',
    'root', '', [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
);

$logs = new LogManager(new PdoLogRepository($pdo));

The PDO repository creates its own prefab_logs table when needed. This is intentional: the Logs module owns the technical schema required to store audit events.

3. Record one event

Add this temporary event first:

$logs->record([
    'action' => 'document.approved',
    'subject_type' => 'document',
    'subject_id' => 1001,
    'actor_id' => 1,
    'message' => 'Document was approved.',
]);

action is a stable machine-readable event name. subject_type and subject_id identify the thing that changed. actor_id identifies who caused the event. message is the human-readable summary.

Checkpoint: After loading the page once, prefab_logs should contain a document.approved event.

4. Record events from a form

Replace the temporary event with:

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $logs->record([
        'action' => $_POST['action'] ?? 'document.updated',
        'subject_type' => 'document',
        'subject_id' => $_POST['subject_id'] ?? '1001',
        'actor_id' => $_POST['actor_id'] ?? '1',
        'message' => $_POST['message'] ?? 'Tutorial event',
        'changes' => [
            'status' => ['old' => 'pending', 'new' => 'approved'],
        ],
        'metadata' => ['source' => 'tutorial-form'],
        'ip_address' => $_SERVER['REMOTE_ADDR'] ?? null,
        'user_agent' => $_SERVER['HTTP_USER_AGENT'] ?? null,
    ]);
}

$recent = $logs->recent(20);

changes stores structured before/after values. metadata holds extra context that does not belong in fixed columns. IP address and user agent can help explain where a browser action originated.

5. Add the browser form

<h1>Prefab Logs Test</h1>
<form method="post">
    <p><input name="action" value="document.approved"></p>
    <p><input name="actor_id" value="1" placeholder="Actor ID"></p>
    <p><input name="subject_id" value="1001" placeholder="Subject ID"></p>
    <p><input name="message" value="Document was approved." size="50"></p>
    <button>Record event</button>
</form>

Submitting the form creates a new immutable historical event. Audit logs are normally appended rather than edited because their purpose is to preserve history.

6. Display recent events

<h2>Recent logs</h2>
<pre><?= htmlspecialchars(print_r($recent, true)) ?></pre>

recent(20) returns the newest 20 records. This is useful for dashboards and general activity feeds.

7. Query by actor or subject

$logs->recent();
$logs->recent(50);
$logs->find(1);
$logs->forSubject('document', 1001);
$logs->forActor(1);

forSubject() answers “what happened to this record?” while forActor() answers “what did this user do?” Those are different audit questions, which is why actor and subject are stored separately.

8. Store structured changes

$logs->record([
    'action' => 'user.updated',
    'subject_type' => 'user',
    'subject_id' => 25,
    'actor_id' => 7,
    'changes' => [
        'office' => ['old' => 'Accounting', 'new' => 'Budget'],
    ],
    'metadata' => [
        'source' => 'admin-ui',
        'request_id' => 'abc123',
    ],
]);

Structured changes are better than hiding everything in one message string because code can later inspect exactly which field changed and what the old/new values were.

9. Human-friendly output

$human = $logs->humanRecent(
    50,
    actorResolver: fn ($id) => "User #{$id}",
    subjectResolver: fn ($type, $id) => "{$type} #{$id}",
);

The database stores IDs because IDs are stable. A human-facing screen can resolve those IDs into names or labels only when displaying the log.

10. Diagnostics

print_r($logs->explain());

Use diagnostics when the module's storage or automatic integration is not being resolved as expected.

Automatic logging and module coexistence

Prefab Logs is designed to coexist with the other modules. When it is installed and configured, it publishes a logger capability that compatible modules can discover, so normal module operations can produce audit records without repeating LogManager::record() throughout application code.

ModuleIntegrationHowWhat happens
UsersAutomatic logginguser.created / user.updated / user.deletedUserManager produces structured changes and sends them to the discovered logger. Actor information can come automatically from Auth.
AuthAutomatic loggingauth.* eventsAuthentication activity can be sent to Logs automatically when Auth discovers the logger capability.
PermissionsAutomatic loggingpermission.granted / denied / clearedPermission changes emit structured log payloads that the Prefab runtime can forward to Logs.
DatabaseAutomatic storage reusedatabase capabilityLogs can build its PDO repository from the shared database without a separate database setup.
Other modules / app codeCompatiblelogger capability / record()Any module can emit a compatible structured payload, or application code can call record() directly for domain-specific events.
Human presentationBuilt-inhuman() / humanRecent()Stored technical events can be converted into human-friendly activity text without changing the raw audit record.

What automatic logging means

Automatic logging does not mean that Logs watches the database. Compatible Prefab modules create a structured audit payload while they perform an operation. If the logger capability is available, Prefab forwards that payload to Logs automatically.

UserManager::update()
    ↓
creates user.updated payload
    ↓
Prefab runtime finds logger capability
    ↓
LogManager records it
    ↓
Auth actor is included when available
Important: Automatic logging only occurs for modules that actually emit compatible log events. Domain-specific actions in application code should still call Logs or emit their own structured event.
